# PRD 010. 작업 방법의 검토와 확인 상태

Status: Complete (Scoped)

Depends on: [PRD 000](000-method-candidate-and-evidence.md) 완료. 뒤 번호 PRD에는 의존하지 않는다.

## Goal

사용자가 후보 방법을 근거와 함께 승인·거절하거나, 반복된 검증 근거를 확인해 사용할 수 있는 방법으로 **승격**한다. **다음 작업에서 방법을 실제 실행하지 않아도 승인/거절 상태와 적용 조건의 조회로 단독 완료한다.**

## Scope

1. PRD 000 후보의 절차·적용 조건·출처와 신뢰 구분·불확실성을 보여주고 사용자 검토 결과 또는 동일 유형의 다른 작업에서 나온 검증 결과를 당시 버전에 결속한다.
2. `candidate`/`confirmed`/`rejected`/`inactive` 의미를 구분한다. 단일 성공·모델 자기평가만으로 승격하지 않으며, 사용자 명시적 확인 또는 서로 다른 작업에서 반복된 검증 결과에 한해서만 확인 상태를 기록한다. 같은 요청·자료에서 나온 여러 실행(재시도, 재요청, 한 요청에서 만든 여러 후보)은 작업 하나의 근거로 세고, 그 반복 결과는 안정성·편차 근거로만 보존한다. 사용자 명시적 확인은 그 방법을 앞으로 기본으로 쓰겠다는 확인이며, 한 작업 결과를 받아들이거나 고른 사실로 대신하지 않는다.
3. 작업 유형·조건별 확인 방법과 원래 버전·판정 근거를 사용자 소유 로컬 조회 표면에 표시한다. 조건 불일치·상충 근거·철회된 확인은 기본 선택 후보로 제시하지 않는다.
4. 신뢰하지 않는 입력(024 quarantine 기준)에서 유래한 후보는 그 출처를 공유하지 않는 작업의 검증 또는 출처와 신뢰 구분을 함께 보여준 사용자 확인으로만 승격한다. 같은 출처를 다시 읽은 작업의 성공은 반복 검증으로 세지 않는다.

## Non Scope

- 확인 방법의 자동 실행, 이후 작업 결과의 품질 보장, 과거 실행의 재작성이나 rollback.
- 033 evaluator를 권한자로 만들거나 005 skill 설치만으로 방법이 확인됐다고 취급하는 것.
- 승격 근거를 만들려고 같은 요청·자료를 여러 방법으로 다시 실행해 대조하는 비교 실행.

## Parent Requirement Mapping

- [038 SPEC](../SPEC.md)의 소유 범위 2와 범위 4의 **적용 가능성 조회·선택 후보** 부분을 소유한다.
- 부모 수용 조건 2 중 승격·정확한 버전/조건 표시·부적합 차단을 소유한다. 실제 다음 작업에서 사용한 결과의 검증은 이 PRD의 종료 조건이 아니다.
- 같은 요청·자료의 반복 실행, 같은 신뢰하지 않는 출처의 반복, 한 작업 결과의 수락을 승격 근거에서 제외하는 규칙을 소유한다.

## Acceptance Criteria

1. 후보 하나를 거절하고 다른 후보를 사용자 명시적 확인 또는 같은 유형의 서로 다른 작업에서 나온 성공·검증으로 승격한다. 근거/버전/적용 조건, 근거별 출처의 신뢰 구분과 현재 확인 상태가 CLI·대화 조회에서 구별된다.
2. 단일 실행 성공, 같은 요청·자료의 반복 실행, 같은 신뢰하지 않는 출처를 공유하는 작업의 반복 성공, 한 작업 결과의 수락, 위조된 실행 ref, 미완료 결과, 상충하는 피드백 또는 조건에 맞지 않는 요청은 기본 후보 승격/선택을 만들지 않는다.
3. 재시작 뒤 같은 방법 버전과 사용자 확인 사실을 조회하며, 확인이 shell·Python·plugin·외부 발송 permission grant를 생성하지 않음을 검증한다.

## Closure Evidence

- 사용자 거절/확인과 추가 검증의 원본 ref·버전·조건이 연결된 전이 및 조회 결과.
- 단일 성공·같은 입력 반복·같은 신뢰하지 않는 출처 반복·결과 수락·오근거·상충 근거·잘못된 적용 조건의 승격 거절 테스트.

PRD 010은 **사용자가 검토할 수 있는 확인 방법 목록**으로 닫힌다. 뒤 번호의 자동 재사용·수정·롤백을 기다리지 않는다.

## 구현 메모 및 검증 근거 (2026-10-24)

아래는 구현·실행 기록이다. 완료 판정은 종료 확인 절에 따로 기록한다.

- **표면:** `shacs-command` `learn.rs`에 `/learn confirm <id>`(검토 화면), `/learn confirm <id> v<N> <code>`, `/learn reject <id> v<N>`, `/learn verify <id>`, `/learn match <request>`를 더했다. `match` 뒤의 요청은 입력한 대소문자 그대로 넘긴다. 모든 하위 명령은 PRD 000과 같은 사용자 turn 판정(`agent_loop_learn::owner_turn`)을 거치고, 명령 응답은 대화 기록에 넣지 않는다. 사용법은 [USAGE](../../../USAGE.md#방법의-확인거절과-다른-작업으로-확인)에 적었다.
- **상태와 결정(`learned_method`, `learned_method_decide`):** 상태는 `candidate`·`confirmed`·`rejected`·`inactive`다. 방법마다 결정 목록(`confirmed`·`rejected`·`verified`·`conflicted`·`repeated`, 결정한 버전·시각·session digest, 확인이면 검토 코드, 다른 작업이면 그 작업의 기록)을 두고, 상태는 현재 버전의 결정을 순서대로 다시 계산해 정한다.
  - 사용자 확인은 `confirmed`로 만든다. `verified`(새 작업이 근거 있는 단계를 모두 다시 함)는 그 버전에 `conflicted`가 아직 없을 때만 후보를 `confirmed`로 만든다. `conflicted`는 `confirmed`를 `inactive`로 만들고, 후보는 그대로 두되 이후 `verified`로 확인되지 않게 한다. `rejected`는 끝이다. `repeated`는 상태를 바꾸지 않는다.
  - 저장 검증(`learned_method_decisions`)은 결정의 형식(검토 코드 8자리, session digest 형식, 다른 작업 기록의 digest·근거 형식, 단계 번호·인용), 다른 작업 기록마다 그 앞의 결정에 비춘 조건(`learned_method_tasks::refused`), 저장된 상태와 다시 계산한 상태의 일치를 확인한다. 결정은 64개까지이며, 다 차면 확인·거절·작업 기록을 그 이유로 거절한다.
- **사용자 확인·거절:** 검토 화면은 `show` 전체(근거별 출처·신뢰 구분·결정)와 확인의 뜻, 권한이 생기지 않는다는 안내, untrusted 영향 경고, 확인 코드를 보여 준다. 코드는 방법 ID·현재 버전·revision·현재 버전 내용의 sha256 앞 8자리다. 저장소의 모든 변경은 lock 안에서 지금 저장된 방법에 적용되고(`LearnedMethodStore::update`) revision을 올리므로, 확인은 lock 안에서 버전과 코드를 지금의 방법과 비교한다. 다르면 다시 검토하라고 하고 바꾸지 않는다. 거절도 버전이 맞아야 한다.
- **다른 작업으로 확인(`learned_method_verify`, `learned_method_verify_evidence`, `learned_method_tasks`):** PRD 000의 근거 수집(`collect`)과 분류 호출을 그대로 쓰고, 대조 호출에는 방법의 목적·적용 작업·전제·근거 있는 단계와 초안 호출과 같은 범위의 근거만 보낸다. 두 호출 모두 도구가 없다.
  - 모델의 답 중 작업 종류·전제 판단만 그대로 쓰고, 단계를 다시 했는지는 runtime이 인용 근거로 정한다. `user_stated` 단계는 그 문장이 그대로 든 `owner` 피드백·절차 메시지, `observed_run` 단계는 그 단계의 도구 각각에 대한 `ok` 호출이 있어야 한다. 어긋남은 `owner` 피드백·절차 메시지를 인용해야 한다.
  - 작업의 신원(`TaskIdentity`)은 요청으로 분류된 메시지의 digest, 사용자가 쓴 모든 메시지의 digest와 시각을 묶은 digest, 도구 결과·첨부 digest, 결과를 가져온 호출의 인자 digest다. 원래 작업의 신원은 후보를 만들 때 근거 창 전체에서 계산해 `origin.task`에 저장하고, 저장된 근거에서 다시 뽑은 것과 합쳐 쓴다. 이 신원과 그 버전에 기록된 모든 작업의 신원에 비해 요청·메시지·결과가 겹치거나, untrusted 영향을 받은 방법에서 출처가 겹치면 다시 한 작업이다. 메시지를 신원에 넣었으므로 분류 호출이 원래 요청을 다르게 분류해도 같은 대화는 다시 한 작업이 된다. 새 작업은 모델이 작업 종류가 맞고 맞지 않는 전제가 없다고 답했을 때 근거 있는 모든 단계를 다시 해야 `verified`로 기록하고, 다시 한 작업은 다시 한 단계가 하나라도 있으면 `repeated`(안정성·편차 근거, 다시 하지 않은 단계도 표시)로, 어긋남은 작업 종류·전제에 대한 모델의 답보다 먼저 보고 새 작업인지와 관계없이 `conflicted`로 기록한다. `repeated`가 원래 근거나 이미 기록된 작업의 근거와 같은 메시지·실행(종류·digest·시각·call ref)만 보여 주면, `conflicted`가 앞선 어긋남이 인용한 피드백만 인용하면 저장하지 않는다. 원래 작업의 피드백도 단계와 어긋나면 기록한다. 저장은 lock 안에서 같은 조건을 다시 확인한다(`record_check`).
  - 작업 결과를 받아들이는 말이나 요청 메시지는 어느 단계도 다시 한 것으로 세지 않는다.
- **재대조(`learned_method_recheck::recheck_check`, `agent_loop_learn_sources`):** 결정에 남긴 근거도 그 작업 session의 지금 기록과 PRD 000 근거와 같은 규칙으로 대조한다. 다시 한 `user_stated` 단계의 문장이 인용 메시지에 남아 있는지도 확인한다. 방법과 결정이 가리키는 모든 session은 명령마다 한 번 읽고 한 번 색인한다. 확인을 만든 `verified` 결정의 근거가 지워졌으면 상태 옆에 "not rechecked"를 붙인다.
- **맞는 방법(`learned_method_match`):** `confirmed` 방법만 도구 없는 호출 한 번으로 요청에 맞는지(작업 종류와 전제)를 묻고, 모델이 맞다고 하고 맞지 않는 전제가 없을 때만 제안한다. 다른 상태의 방법은 보내지 않고 이유와 함께 나열하며, `confirmed`가 없으면 호출하지 않는다. 아무것도 실행하지 않는다.
- **권한:** 확인은 permission rule·grant를 만들지 않는다. `permission_rules`에 보호 대상 종류 `LearnedMethods`를 더해 `.shacs-methods`가 들어간 경로를 보호 대상으로 분류했다. static rule의 거절이 권한 모드 판단보다 먼저이므로 모든 모드에서 파일 도구가 막히고, `auto`는 묻되 승인해도 실행하지 않는다(기존 보호 대상 처리).
  - 권한 단계는 인자에 적힌 경로만 본다. 그래서 파일 도구도 경로를 해석한 뒤 확인한다(`tools::filesystem::refuse_learned_methods`). 실제 경로(symlink를 따라간 canonical 경로)가 `.shacs-methods` 안이거나 저장 폴더 파일의 hard link(Unix의 장치·inode 비교)이면 거절한다.
  - 폴더를 훑을 때 `list_dir`·`glob`·`grep`은 `.shacs-methods` 이름을 건너뛰고(`ignored_name`), `grep`은 저장 파일의 hard link도 읽지 않는다. 셸 명령·Python·`message` 첨부는 기존 승인 경계를 따른다.
- **PRD 000에 생긴 변경:** 실행 판정에서 `read_file`의 `[File unchanged since last read: …]` 답(같은 실행 안의 읽기 캐시)을 `incomplete`로 본다. 이 답은 그 작업에서 아무것도 읽지 않았고, 결과 digest가 달라져 같은 자료 판정을 피할 수 있기 때문이다. 목록에 적용 작업을 보인다.
- **테스트(최소):** `shacs-command` router의 `/learn` 파싱 테스트에 새 하위 명령을 더했다. `shacs-core` `tests/it` `spec038_learned_methods`에 12개를 더했다(전체 31개).
  - `review`: 검토 코드·버전이 다르면 거절하고, 확인 뒤에도 쓰기 도구는 승인을 묻고 실행되지 않으며, 재시작 뒤 확인 사실을 읽는다. 확인된 방법만 맞는 요청에 제안되고, 거절·후보·전제 불일치는 제안되지 않는다.
  - `checks`: 같은 작업은 세지 않고 다른 작업이 확인한다. 근거가 지워진 확인을 표시한다. 원래 대화는 분류만 다르게 받아도 다른 작업이 되지 않는다.
  - `conflicts`: 어긋남이 이후 확인을 막고 확인된 방법을 사용 중지한다. 원래 작업의 피드백과 어긋나는 단계도 기록하고, 모델이 작업 종류가 맞지 않는다거나 맞지 않는 전제가 있다고 답한 작업의 어긋남도 기록한다.
  - `store_access`: 실제 파일 도구로 확인한다. `list_dir`·`glob`·`grep`(경로 없이)이 저장 파일의 이름·내용을 보이지 않는다. 저장 폴더로 가는 symlink나 저장 파일의 hard link로는 읽기·쓰기·고치기를 거절하며, 저장 파일은 바뀌지 않는다.
  - `checks_refused`: 실패한 실행, 없는 근거 ID, 실행 단계에 사용자 말 인용, 결과 수락, 맞지 않는 작업은 저장하지 않는다. 같은 자료의 재실행은 안정성 근거로만 남기고, 같은 작업 안의 어긋남을 한 번만 기록한다. untrusted 출처를 다시 읽은 작업은 세지 않는다.
  - `edits`(PRD 000 파일): 결정이 다 찬 방법은 거절 등을 그 이유로 거절한다.
  - PRD 000의 `records` 테스트에 읽기 캐시 답의 판정 assert를 더했다. `shacs-core` `permission_policy`의 보호 대상 테스트에 `.shacs-methods` 경로를 더했다. `shacs-cli` compiled REPL 테스트에 재시작 뒤의 확인과 다시 재시작한 뒤의 목록을 더했다.
- **실제 CLI QA:** 격리된 config·workspace와 fake provider로 compiled `agent` REPL을 tmux에서 실행했다.
  - 1차(`.omo/evidence/spec038/prd010/qa1/`, 예비): 확인·거절·다른 작업 확인·어긋남·`match`·저장 보호 흐름을 확인했다. 이때 다시 한 작업의 결과를 남기지 않는 점과 이미 센 작업 안의 어긋남을 기록하지 않는 점을 찾아 고쳤다.
  - 2차(`qa2/`): 같은 흐름을 고친 실행 파일로 다시 확인했다. 같은 작업의 확인 거절, 다른 session의 작업으로 확인, 바뀐 파일을 같은 요청으로 다시 읽은 실행의 안정성 근거 기록, 새 process에서의 상태 유지, 어긋남의 한 번 기록과 사용 중지, 사용 중지 중 model 없이 끝나는 `match`, 검토 코드로 다시 확인한 뒤의 제안, 모델의 `write_file`로 저장 파일을 쓰려는 시도의 거절과 파일 무변경, 확인 뒤에도 묻는 다른 쓰기 도구를 확인했다. 준비한 응답이 모두 소비됐다.
  - 3차(`qa3/`, 1차 gate 지적 수정 뒤):
    - 모델이 `fits: false`로 답한 다른 작업에서도 사용자의 어긋나는 피드백이 기록됐다.
    - 경로 없는 `grep`은 저장 파일에만 있는 글을 찾지 못했다. `glob`에는 hard link의 이름만 보였다.
    - 저장 폴더로 가는 symlink와 저장 파일의 hard link로 `read_file`하면 거절됐다. hard link에 대한 `write_file`은 승인을 받은 뒤에도 도구가 거절했다.
    - 저장 파일의 sha256과 inode는 바뀌지 않았다.
  - 고치기 전 코드에서 새 테스트가 실패한 기록은 `gate1-fixes/`에 있다.
  - 기록은 로컬 `.omo/evidence/spec038/prd010/`에 있으며, 이 evidence가 없는 checkout에서는 실행 증명으로 보지 않는다.
- **독립 검토:** 1차 gate는 BLOCKED였고 지적은 세 가지였다.
  1. 모델이 작업 종류가 맞지 않는다고 답하면 함께 보고된 어긋남도 버려졌다.
  2. `grep`처럼 폴더를 훑는 파일 도구가 경로를 주지 않으면 저장 파일을 읽을 수 있었다.
  3. 저장 파일만 고쳐도 사용자 확인을 꾸밀 수 있는데, 문서는 session 파일까지 함께 고쳐야 한다고 적었다.
  - 1·2는 고쳤고, 고치기 전 코드에서 실패하는 테스트(`conflicts`·`store_access`)를 더했다. 2는 symlink·hard link로 가리키는 경우까지 막았다. 3은 아래 남은 제한과 USAGE에 바로 적었다.
  - 2차 gate는 PASS였다(아래 종료 확인).
- **남은 제한:**
  - 같은 작업인지는 요청 글·사용자 메시지·도구 결과·호출 인자의 digest로만 본다. 표현을 바꿔 다시 요청하고 자료도 달라졌으면 새 작업으로 셀 수 있고, 근거 창에 앞 요청이 남아 있으면 같은 대화의 다른 요청도 다시 한 작업으로 본다. 같은 출처는 호출 인자가 글자 그대로 같을 때만 같다(`./notes.md`와 `notes.md`는 다르다).
  - 작업 종류·전제가 맞는지와 어긋나는 피드백이 있는지는 모델의 판단이다. runtime은 모델이 든 근거가 그 판단을 뒷받침할 수 있는 종류인지만 확인한다.
  - 저장 파일은 인증된 기록이 아니다. 읽을 때의 검사는 결정의 형식과 앞뒤 조건만 본다. 그래서 저장 파일만 고쳐도(예: 셸 명령 승인) 사용자 확인(`confirmed`와 8자리 코드)을 꾸밀 수 있다. 사용자 확인은 session 기록과 대조하지 않는다. 다른 작업의 확인도 근거가 없는 session을 가리키게 꾸미면 "not rechecked"로만 표시된다.
  - 원래 작업과 다른 작업 기록의 신원 digest는 그 작업의 근거 창 전체에서 계산해 저장하므로 다시 계산할 수 없다. 파일 도구의 저장소 보호는 모델이 파일 도구로 이런 기록을 바꾸는 것만 막는다.
  - 확인 코드는 사용자가 검토 화면을 봤다는 표시이며 비밀이 아니다(명령 응답은 대화 기록에 넣지 않으므로 모델은 보지 못한다).

## 후속 변경 (PRD 020 작업, 2026-10-24)

PRD 020을 구현하며 이 PRD의 동작에 다음이 더해졌다. 위 종료 판정의 범위는 바뀌지 않는다.

- `/learn match`의 판단 호출에 단계 글을 함께 보낸다. 요청이 결과의 모양을 정했는지와 모양을 정하는 단계도 받아, 맞는 방법에서 빠질 단계를 표시한다.
- 사용자가 사용을 멈춘 방법도 `inactive`다. 제안하지 않는 이유는 어긋남과 사용 멈춤을 구분한다.
- 결정 종류에 고치기·사용 멈추기·되돌리기가 더해졌다. 저장 검증은 버전과 결정의 흐름도 확인한다([PRD 020](020-method-reuse-edit-and-revert.md)).
- 거절된 버전의 검토 요청에는 고치기·되돌리기를 안내한다.
- 확인된 방법이 있으면 일반 요청마다 그 방법을 쓸지 판단하는 호출이 한 번 더 든다.
