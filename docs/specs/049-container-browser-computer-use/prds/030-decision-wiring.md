# PRD 030. 브라우저 판정 연결

Status: Complete (Scoped)

Depends on: PRD [000](000-tool-result-images.md)·[010](010-container-browser-and-boundary.md)·[020](020-browser-tool.md)의 닫힌 결과와 048 PRD 000–050의 닫힌 판정·비밀 값 가리기·도구 결과 검사. PRD 040과 050·051의 구현에 의존하지 않는다.

## Goal

브라우저에서 보는 일과 페이지를 바꾸는 일을 동작마다 구별한다. classifier와 승인 질문은 요소 번호 대신 사이트·버튼·입력·양식의 내용을 보고 판정한다. 020의 임시 bypass 전용 제한을 제거하고 부모 스펙의 모든 mode 판정을 완성한다.

## 지금 상태

- `SafetyCapability`는 `FsRead`부터 `SelfModification`까지 열 항목이며 `SafetyCapability::parse`, `SafetyCapability::all`도 그 집합을 쓴다(`crates/shacs-config/src/permissions.rs`). `browser_act`는 없다.
- `normalize_tool_candidate`는 `tool_capabilities(registry, tool_name)`을 부르고 인자만으로 target을 만든다. `infer_capabilities`는 tool 이름과 process adapter만 본다(`crates/shacs-core/src/runtime/permission_action.rs`). 현재 페이지의 요소 설명은 인자에 없으므로 번호만으로는 판정할 수 없다.
- `decide_plan`은 `FsRead`만 허용하고 나머지를 거절한다. default·accept_edits는 읽기·쓰기 이외를 `ask_or_deny`로 보낸다(`crates/shacs-core/src/runtime/permission_policy.rs`의 `decide_plan`, `decide_default`, `decide_accept_edits`). 따라서 plan의 browser 읽기 허용과 act 질문은 browser에 한정한 명시적 추가 처리가 필요하다.
- `parse_specifier`는 `web_fetch`에만 `domain:`을 받으며 known tool 목록에 browser가 없다(`crates/shacs-core/src/runtime/auto_mode/permission_rule.rs`). `blocking_match`의 host 분기도 `web_fetch`만 본다(`crates/shacs-core/src/runtime/auto_mode/rule_match.rs`). parser만 넓혀서는 browser 규칙이 적용되지 않는다.
- `AutoModeSlots::resolve`가 쓰는 `DEFAULT_SOFT_DENY`는 일곱 항목이다(`crates/shacs-core/src/runtime/auto_mode/classifier_slots.rs`). 구매 등 계정 동작 항목은 있지만 browser 확정 전용 항목은 없다.
- `normalize_tool_candidate`는 `action_secrets::argument_views`로 판정용 값과 노출용 값을 구별한다(`crates/shacs-core/src/runtime/permission_action.rs`). `result_check::checked_text`는 content-part 배열이면 text만 고른다(`crates/shacs-core/src/runtime/auto_mode/result_check.rs`). PRD 000의 `tool_images::persist`는 그 검사 전에 그림을 파일 참조 글로 바꾼다(`crates/shacs-core/src/runtime/tool_images.rs`).

## Scope

1. **새 capability:** `SafetyCapability::BrowserAct`를 더하고 serde·label·parse에 `browser_act`, `all()`의 집합에 열한 번째 항목을 넣는다. core의 capability label/검증과 classifier eligibility의 exhaustive match, diagnostics 직렬화, config schema·허용값 목록과 상속 ceiling 비교를 모두 같은 값으로 맞춘다. `browser_act`는 `net_outbound`, `proc_exec`, `external_delivery`와 별도다. 부모 ceiling에 이 값이 없으면 browser act를 허락하지 않으며, 다른 capability가 대신 만족시키지 않는다. `runtime_capability_ceiling_from_registry`(`crates/shacs-cli/src/lib.rs`)의 020 browser 분기를 확장해 새 production ceiling에는 `net_outbound`와 `browser_act`를 모두 광고한다. 이 작업은 030 소유다. 새 프로필에서 모든 capability를 뜻하는 집합은 `all()`을 소비하게 하고 기존 저장 ceiling에 없던 값을 자동으로 보태지 않는다.
2. **동작별 정규화:** 직접 호출·deferred bridge·승인 뒤 실행이 공용 정규화를 쓰도록 동작 인자를 읽는다. `open`, `look`, `scroll`, `back`, `wait`, `close`는 `[NetOutbound]`, `click`, `type`, `press`는 `[BrowserAct]`다. tool은 `process_adapter_kind: None`을 유지한다. session·mode·대화형 여부는 020이 실행 경로에 채운 `BrowserCallContext`와 동일한 run snapshot을 사용하고 registry나 model 인자에서 새로 추정하지 않는다. 잘못된 action은 capability 없는 정상 동작으로 바꾸지 않고 정규화 오류로 거절한다. 020의 bypass 전용 실행 guard와 전 동작 net 임시 분기를 이 PRD에서 제거한다. 010의 user-local enable 기반 시작 허락과 browser 전용 gate는 바꾸지 않는다.
3. **판정 설명과 고정된 실행 대상:** host가 가진 최신 검증 snapshot에서 판정용 browser action을 준비한다. 모델이 `origin`·역할·양식 정보를 인자로 자가 신고하게 하지 않는다. 준비는 페이지 변경·캡처·새 browser 시작 없이 수행한다. `open`은 요청 URL, 다른 동작은 현재 주 문서 origin을 사용한다. `click`·`type`은 해당 요소, `press`는 현재 focus 요소를 설명한다. focus나 form이 없으면 `none`이라고 명시한다.
    - 설명에는 action, origin, role, accessible name, type의 입력 text·submit 여부 또는 press key, 실제 연결된 form의 accessible name과 DOM에서 해석한 절대 submit URL·method를 넣는다. form owner는 DOM의 실제 소속(`form` 속성으로 외부에 연결된 경우 포함)으로 정한다. 제출에 쓰일 submitter의 node id와 `formaction`·`formmethod`·`formenctype`·`formtarget`·`formnovalidate` override를 기록하고 URL·method 등 최종 제출 속성에 반영한다. URL은 현재 document base URL로 해석한다. Enter의 제출 대상이나 submitter를 확인할 수 없으면 추정한 대상에 승인받지 않고 다시 관찰하라는 거절을 반환한다. 양식이 없으면 URL도 none이다. 번호는 참고로만 남기며 설명의 유일한 근거가 될 수 없다.
    - 원본과 노출본을 구별하고 모든 설명 문자열에 022 `redact_value`/`redact_string`과 048 `.env.json` 값 가리기를 적용한다. 이름·form·URL도 페이지가 준 비신뢰 자료다. URL userinfo와 비밀 query 값도 redaction 대상이다. 8자 이상 `.env.json` 값은 `[secret 이름]`이고 classifier·질문·diagnostics·로그에 원문이 없다. 048처럼 값 snapshot을 읽지 못하면 classifier는 판정 없음이다.
    - 원래 tool 인자·snapshot revision·target/frame/loader·origin·요소/form 설명·form owner·submitter node와 override·해석된 최종 제출 URL/method 등의 원본 digest를 action digest와 승인 correlation에 묶는다. `press`는 정확한 focused frame과 실제 focused node도 포함하고 shadow root와 자식 frame의 실제 focus까지 확인한다. 노출용 마스킹 때문에 다른 입력이 같은 승인으로 실행되지 않게 한다.
    - classifier 허용·승인 후 실제 Input event 직전에 DOM에서 대상의 존재·역할/이름, 실제 form owner, 제출 URL·method, submitter node와 모든 override를 다시 읽어 binding과 비교한다. `press`는 실제 focused frame/node도 다시 읽는다. 020 click의 올바른 frame hit-test도 유지한다. loader·URL·revision이 같더라도 form action, base URL, 소속 form, method, submitter override 또는 focus가 바뀌면 입력하지 않고 기존 binding을 무효로 한다. 결과는 다시 look하고 새 판정을 받으라는 안내이며 자동으로 새 대상에 승인이나 classifier 결과를 재사용하지 않는다.
    - 페이지가 아직 없을 때 open·close는 요소 없이 준비할 수 있다. 읽기 동작의 판정 준비가 내부 문서를 읽는 우회로가 되지 않게 010의 검증된 자료만 사용한다. snapshot이 없거나 다른 session 소유면 실행 가능하지 않다는 이유를 돌려주며 새 페이지를 읽어 설명을 채우지 않는다.
4. **022·048 판정 자리:** 상속 한도·인자 오류·사용자 deny/ask·승인 correlation 등 기존 선행 규칙을 그대로 적용한 뒤 다음 baseline을 쓴다. 사용자 allow와 기억된 승인도 048의 기존 자리·범위를 따르며 tool의 password/file/문서 검사를 풀지 못한다.

   | mode/실행 | `net_outbound` 동작 | `browser_act` 동작 |
   |---|---|---|
   | auto(대화형) | `web_fetch`와 같은 048 4단계 classifier | 048 4단계 classifier. 허용만 실행 |
   | default, accept_edits | 기존 `web_fetch` 판정 | 대화형은 승인 질문 |
   | plan | browser의 open/look/scroll/back/wait/close 허용. `web_fetch`는 기존 거절 유지 | 대화형은 승인 질문, 비대화형은 거절 |
   | dont_ask | 기존 `web_fetch` 판정 | 거절 |
   | 비대화형(bypass 외) | 기존 `web_fetch` 판정, plan의 browser 읽기는 위 예외 적용 | 거절 |
   | bypass_permissions(대화형·비대화형) | 기존 `web_fetch` 판정 | 허용. 기존 deny/ask·상속 한도는 적용 |

   대화형 auto classifier 막음·판정 없음은 실행하지 않고 048의 거절 누적·계속 진행·임계치 질문을 그대로 따른다. `browser_act`의 비대화형 non-bypass와 `dont_ask`는 allow·기억된 승인·classifier로 실행 가능해지지 않으며 질문이나 classifier 요청 없이 거절한다. bypass는 대화형·비대화형 모두 실행하되 기존 사용자 deny/ask와 상속 한도를 유지한다. 비대화형의 ask 규칙은 기존처럼 거절이다.

   `decide_plan`(`crates/shacs-core/src/runtime/permission_policy.rs`)의 예외는 정규화된 실제 tool이 `browser`이고 동작과 capability가 Scope 2에 맞을 때만 적용한다. browser의 여섯 net 동작은 대화형·비대화형 모두 baseline 허용, 세 act 동작은 대화형 질문·비대화형 거절이다. generic `NetOutbound` 전체를 plan에 허용하지 않는다. `web_fetch`·다른 tool·다른 capability와 기존 선행 규칙은 그대로다.
5. **classifier·승인 입력:** 공용 action 설명을 classifier pending action과 승인 질문에 함께 넣는다. classifier는 048 transcript 규칙(사용자 메시지·앞선 도구 호출만, 도구 결과·assistant 글 제외)과 16,000자 action 한도를 유지한다. 설명까지 잘리면 `truncated`다. 승인 질문은 origin·역할·이름·입력·form과 제출 대상을 보이고 022 선택지·correlation·가린 비밀이 있는 질문의 일회 승인 계약을 유지한다. 준비된 정보는 tool 결과가 아니며 페이지 지시문을 system 안내로 삽입하지 않는다.
6. **기본 soft deny:** `DEFAULT_SOFT_DENY` 끝에 다음 한 줄만 더한다. 사용자 override와 `$defaults` 의미는 그대로다.

   ```text
   - [Browser Commitment] In the browser, submitting or confirming a purchase, booking, payment, message, post, or account-setting change the user did not ask for.
   ```

   048의 직접적·구체적인 사용자 의도 또는 ALLOW 예외만 soft deny를 푼다. 클릭 호출의 모델 설명·tool 결과·승인 답을 새 사용자 메시지로 만들지 않는다. hard deny는 그대로 우선한다.
7. **사용자 규칙:** known tool에 `browser`를 넣고 `browser`, `browser(domain:<host pattern>)`만 더한다. action 이름 지정 같은 새 문법은 없다. `HostPattern`의 기존 대소문자·끝 점 제거·`*`·`*.example.com` 의미를 그대로 쓴다. open은 요청 URL의 host, 나머지는 현재 검증된 주 문서 origin의 host가 subject다. close에 현재 문서가 없으면 domain 규칙은 맞지 않고 bare browser는 맞는다. browser/web_fetch 사이에 domain 규칙이 새지 않도록 parser와 deny·ask·allow matcher 모두 selector를 확인한다. deny → ask → allow의 기존 우선순위와 비대화형 ask 거절을 유지한다. 승인 뒤 origin이 바뀌면 규칙을 적용했던 action은 실행하지 않는다.
8. **결과 검사:** 실제 실행한 browser 결과의 text만 기존 048 검사로 보낸다. 000 저장 뒤 URL·제목·요소·보이는 글·그림 참조 text가 대상이며, PNG/base64·provider 요청에만 붙인 그림 메시지는 요청에 없다. 걸리면 기존 경고를 덧붙이고 결과를 지우거나 새 승인을 요구하지 않는다. permission 거절·스키마 오류 등 실행하지 않은 호출은 검사하지 않는다. 검사 실패와 classifier 부재는 기존 diagnostics만 남긴다.
9. **문서:** `docs/USAGE.md`와 README 권한·브라우저 문단에서 020 임시 제한 설명을 최종 표로 교체한다. `browser_act`, domain 예, soft deny의 확정 동작과 명시 의도, 요소 이름의 불신·캡처 미검사를 적는다. 앞선 022·048 스펙과 닫힌 PRD 본문은 고치지 않는다.

## Non Scope

- browser 시작 gate와 proxy 판정, viewer, 다른 tool capability·mode 변경.
- classifier template 전체 변경, 사용자 규칙의 새 action 문법, tool 결과의 그림 검사.
- 050 handoff·takeover·로그인, 051 감시의 비대화형 읽기.

## Required Contract

1. 동작의 capability는 하나이며 `browser_act`를 다른 capability로 대신 승인하지 않는다.
2. classifier·승인 질문은 host가 검증한 내용 설명을 받고, 승인과 실행은 같은 snapshot·인자·focus·form/submitter binding에 묶인다. 입력 직전 DOM 재확인에서 same-loader 변경도 거절한다.
3. 대화형 auto는 048 4단계를 따른다. plan은 browser 읽기를 허용하고 act는 대화형 질문·비대화형 거절이다. bypass act는 비대화형도 실행하며 그 밖의 비대화형 act와 dont_ask는 거절한다. 선행 사용자 규칙과 상속 한도를 건너뛰지 않는다.
4. browser domain은 해당 tool과 실제 판정 대상 host에만 맞는다.
5. soft deny 문장은 부모 표와 한 글자까지 같고, 결과 검사는 text만 본다.
6. `Cargo.lock`에 새 crate를 더하지 않는다.

## 구현 결정 (2026-11-10)

PRD 본문이 열어 둔 선택은 다음과 같이 정했다.

- **설명과 digest의 전달 자리:** host가 준비한 설명은 정규화(`permission_action.rs`의 `normalize_tool_candidate`)에서 판정용 인자에 `browser_action`으로, host digest는 `browser_binding_digest`로, 원본 인자의 별도 digest는 `browser_argument_digest`로 넣는다. 그래서 기존 classifier payload(`classifier_request.rs`의 16,000자 clip·`truncated`), 승인 질문의 `Arguments`, action digest·approval correlation, `.env.json` 가리기(`hidden_browser`가 노출본과 판정본을 분리해 가린 호출은 일회 승인)가 template 변경 없이 그대로 적용된다. tool의 `preflight_refusal`에는 이 세 key를 뺀 원본 인자만 준다(`action_materials.rs`).
- **준비 실패의 결과:** host가 준비하지 못한 호출(지난 revision, 다른 session의 브라우저, 페이지 없는 조작, 확인할 수 없는 Enter 제출 대상)은 `InvalidArguments` 정규화 오류다. 거절 글에는 host의 이유(`browser_stale_revision: 다시 look하세요` 등)를 담아 모델이 다시 `look`할 수 있게 한다(`tool_execution.rs`의 `PermissionEvaluation::block_message`). 준비는 `BrowserHost::prepare`가 manager 잠금을 `try_lock`으로 잡고 마지막 검증 snapshot만 읽으며 브라우저를 띄우거나 CDP를 보내지 않는다.
- **mode 경계의 위치:** 비대화형 non-bypass와 `dont_ask`의 `browser_act`는 상속 한도, 정규화·정적 거절, 사용자 deny·기억된 deny 뒤에, 승인·allow·기억된 allow·classifier 앞에서 거절한다(자세한 순서는 아래 "mode 금지의 우선순위"). 그래서 질문·classifier 요청·CDP 입력이 없다. `plan` 예외는 정규화된 tool 이름이 `browser`이고 action과 capability가 Scope 2와 일치할 때만(`permission_policy.rs`의 `browser_mode_action`) 적용하고, generic `NetOutbound`에는 열지 않는다. classifier eligibility는 `BrowserAct`를 대화형일 때만 인정한다(`runner.rs`).
- **classifier 심사 뒤의 대상 고정:** auto mode에서 classifier가 본 action digest를 실행 context에 `browser_reviewed_action_digest`로 고정하고, 실행 직전 재정규화의 digest가 다르면(심사 뒤 origin·요소가 바뀜) 거절한다(`tool_execution.rs`의 `permission_evaluation_for_action`).
- **입력 직전 재확인:** `CdpDocument::execute_prepared`가 digest를 다시 계산해 비교하고, 각 `Input.*` 직전에 `recheck_binding`이 문서(target·frame·loader)와 대상 요소의 실제 form owner·submitter·override·제출 URL/method, `press`의 deep focus(shadow root·자식 frame)를 DOM에서 다시 읽어 digest를 비교한다. 불일치면 입력 없이 snapshot을 버려 binding을 무효로 하고 `browser_stale_revision`을 돌려주며 브라우저 generation은 유지한다. 020의 hit-test는 그대로 그 앞에 있다. `type`의 `submit`과 `press`의 Enter는 실제 submitter(기본 submitter 또는 눌린 submit 버튼)와 그 `form*` override를 제출 속성으로 쓴다.
- **입력 연쇄 전체에 걸친 binding(독립 검토 1·2차 지적):** click은 `mousePressed` 뒤, 확정 이벤트인 `mouseReleased` 직전에 binding을 한 번 더 재확인한다. mousedown handler가 같은 loader 안에서 form action·submitter를 바꾼 것이 여기에 걸린다. 불일치면 어떤 입력도 더 보내지 않고 `browser_document_changed`로 끝내며, manager가 그 generation을 버려 브라우저 process를 끝낸다(`CdpDocument::terminate`, `BrowserManager::with_generation`). 다른 곳에서 버튼을 놓아 취소하는 방식은 쓰지 않는다. pointerdown handler의 `setPointerCapture`는 다른 곳의 release도 그 버튼의 click으로 만들고, 공통 조상이 `label`·`a`면 조상이 activation하며, 놓는 지점으로 가는 `mouseMoved` 사이에 page handler가 대상을 옮길 수 있어 페이지 상태와 무관하게 activation을 막는 브라우저 수준의 취소가 없기 때문이다. 이미 보낸 첫 이벤트(mousedown, keydown)는 되돌리지 못한다. 키 입력: 허용한 열네 키의 activation은 `keyDown`에서 일어난다. link는 DOM keydown에서, button은 keypress에서 activation하고, CDP `keyDown`에 `text: "\r"`을 넣은 Enter는 keydown과 keypress를 함께 만들어 암시적 제출과 버튼 activation이 `keyUp` 전에 끝난다. 그래서 `keyDown` 직전에 재확인하고, `keyDown` 뒤 `keyUp` 직전에 한 번 더 재확인해 불일치면 `keyUp`을 보내지 않고 같은 방식으로 브라우저를 끝낸다. 페이지가 keyup handler에 정한 동작은 `keyUp`을 보내지 않음으로써 일어나지 않지만, keydown·keypress에 정한 동작은 이미 일어난 뒤다.
- **Enter의 submitter(독립 검토 1차 지적):** focus된 요소가 submit control(`button[type=submit]`, `input[type=submit|image]`)이면 그 요소 자신과 `form*` override가 submitter다. 암시적 제출이 일어나는 text계 `input`만 form의 기본 submit 버튼을 쓴다. 그 밖(checkbox·radio·`type=button`·link·textarea 등)은 submitter가 없고, form이 있으면 확인할 수 없는 제출로 보고 거절한다(`browser_action_binding.rs`의 `ENTER_SUBMITTER`).
- **검증 문서 자료와 act binding의 분리(독립 검토 1·2차 지적, Docker 확인):** `CdpDocument`는 번호 binding(`snapshot`)과 별도로 마지막 검증된 주 문서(`verified`: target·session·frame·loader·URL)를 둔다. 읽기가 성공하면 둘 다 갱신되고, 주 frame의 `Page.frameNavigated`·`Page.navigatedWithinDocument`는 DevTools가 알린 URL로 `verified`를 갱신하며(http가 아니면 비움), 자식 frame 이동·target 부착 같은 다른 이벤트는 `snapshot`만 버린다. `look`·`scroll`(요소 없음)·`back`·`wait`·`close`는 `verified`만으로 준비하고 revision·epoch를 digest에 넣지 않는다. 실행(`execute_prepared`)은 먼저 밀린 이벤트를 모두 처리한 뒤 digest를 다시 계산해 비교하고, `open`·`close`가 아니면 `Page.getFrameTree`로 지금 주 문서를 읽어 판정 때의 `verified`와 같을 때만 읽거나 동작한다. 다르면 읽지 않고 `verified`를 지금 문서로 바꾸어 `browser_stale_revision`을 돌려주므로 다음 판정은 실제 문서(그 origin의 규칙)로 이루어진다. `look`의 읽기 transaction도 시작 문서가 판정 문서와 같아야 한다. `scroll`·`back`·`wait`는 판정 문서를 실행 전체에 가지고 간다(독립 검토 3차 지적): 이벤트를 처리한 뒤 `verified`가 판정 문서와 같아야 하고, 각 단계(`wait`의 매 반복, `scroll`의 이동, `back`의 시작)에서 지금 주 문서를 읽어 같을 때만 진행하며, `scroll`·`wait`의 결과 읽기도 그 문서로 제한한다. `back`은 이동이 목적이므로 시작 문서를 확인한다: 들어갈 때, 그리고 `Page.getNavigationHistory`(이벤트를 처리하는 요청) 뒤 `Page.navigateToHistoryEntry` 직전에 다시 확인하고, 기록이 있어 실제로 이동했을 때만 결과 읽기를 제한하지 않는다. 기록이 없으면 결과 읽기도 판정 문서로 제한한다(독립 검토 4차 지적). 다르면 읽지 않고 `browser_stale_revision`이다. 새 target(popup)으로 바뀌면 opener의 identity를 옮기지 않고 `verified`를 비운다. 새 target의 identity는 그 target 자신의 session이 알린 주 frame `Page.frameNavigated`(http(s) URL)나 그 target의 검증된 읽기에서만 온다. 다른 session의 `Page.frameNavigated`·`Page.navigatedWithinDocument`는 `verified`를 바꾸지 않는다(이전 target의 늦은 이동 이벤트가 새 target의 identity가 되지 않게). click이 연 popup은 그 click의 결과 읽기가 popup 문서를 검증해 돌아오고(PRD 020 범위 7), 이후 판정은 popup의 origin으로 한다. 새 target에 아직 http(s) 문서가 없으면(`about:blank`) 관찰은 준비되지 않고(`browser_document_changed: 페이지를 다시 여세요`) `open`이 필요하다. 페이지가 없는 generation(새 browser)에서도 open·close만 준비된다.
- **popup 부착의 처리 시점(Docker 확인):** 실제 Chromium은 `Target.setAutoAttach`의 `waitForDebuggerOnStart`로 멈춘 새 창을 opener의 renderer를 막아 기다린다(`window.open`을 부른 click handler가 `Runtime.runIfWaitingForDebugger`까지 돌아오지 않는다). 그래서 popup을 연 `Input.dispatchMouseEvent`의 응답은 popup을 재개하기 전에는 오지 않고, 응답을 받은 뒤 이벤트를 처리하던 이전 구현은 page deadline까지 멈췄다(`browser_page_timeout`). 지금은 전송 계층(`DevToolsPeer::request`)이 응답을 기다리는 동안 `waitingForDebugger`인 page target 부착을 보면 즉시 `admit_paused_target`을 불러 그 browser context의 download 거절, `Page.enable`·`DOM.enable`·file chooser 가로채기를 새 session에 설치하고 `Runtime.runIfWaitingForDebugger`를 보낸 뒤 원래 응답을 계속 기다린다. 처리한 이벤트는 `waitingForDebugger`를 지워 돌려주고, 문서 계층은 그 이벤트로 target을 바꾸고 이전 탭을 닫는다. 새 target은 `about:blank`에서 http(s) 문서로 가서 `document.readyState`가 `complete`가 된 뒤에만 읽어, 적재 중의 제목·target 이벤트가 읽기 도중의 변경으로 잡히지 않게 한다. 전송 계층은 멈춘 부착 이벤트를 받은 그 자리에 먼저 넣어 두고(slot 예약) 처리를 시작하며, 처리가 끝나면 그 이벤트에 `admitted`를 표시한다. 처리 중 도착한 또 다른 부착과 이동 이벤트는 그 뒤에 도착 순서대로 남고, 중첩 대기 중 도착한 바깥 응답은 보관한다. 문서 계층(`CdpDocument::events`)도 재진입하지 않는다: 받은 이벤트는 하나의 FIFO(`inbox`)에 넣고 적용 중에 보낸 명령(target 닫기, 설정, 캡처 정리)이 받은 이벤트는 앞서 쌓인 것 뒤에 붙어 바깥 적용이 순서대로 처리한다(독립 검토 4차 지적). 그래서 생성 순서대로 target을 바꾸고 마지막 popup만 남긴다(`popups_attached_while_switching_keep_creation_order`). 표시된 이벤트는 문서 계층에서 다시 설정하지 않는다. 중첩 처리 깊이는 `MAX_ADMISSION_DEPTH`(4)까지이며 넘으면 `browser_protocol`로 끝내 manager가 generation을 버린다(가짜 pipe 시험 `pipe_admits_overlapping_popups_in_arrival_order`, `pipe_admission_nesting_is_bounded_and_fatal`). 가짜 peer 시험(`popup_attach_is_admitted_while_the_click_reply_is_pending`)은 재개 전에 응답을 내지 않는 실제 순서를 그대로 흉내 낸다. generation을 만지는 host 진입점(`execute_prepared`·`read`·`act`·`current_document`의 `with_generation`, `close_prepared`, maintenance의 idle·process 확인)은 같은 결과 규칙(`BrowserManager::dispose_on_fatal`)을 쓴다: `browser_stale_revision`·`browser_target_covered`·`browser_input_denied`만 브라우저를 유지하고, 다른 오류(문서 변경, file chooser·download, 전송·protocol 오류, 시간 초과)는 즉시 generation을 버려 process·proxy·프로필을 정리하고 `Failed`를 기록한다. 준비된 `close`도 예외가 아니다(독립 검토 4차 지적, `prepared_close_disposes_the_generation_on_a_fatal_error`). `BrowserError`는 모든 변형이 `browser_<코드>: <안내>` 글을 가진다(`browser_PageTimeout`같은 Debug 꼴은 없다). `browser_page_timeout`은 manager가 generation을 버리므로 다시 열라고 안내한다.
- **mode 금지의 우선순위(독립 검토 1·2차 지적):** 비대화형 non-bypass·`dont_ask`의 `browser_act` 거절(`unattended_browser_act_denial`)은 상속 한도, 정규화·정적 거절, 사용자 deny·기억된 deny 뒤에, 승인·allow·기억된 allow·classifier 앞에 온다(auto는 `auto_decision.rs`의 승인 행 앞, 다른 mode는 `decide_without_user_rules`의 기억된 deny 뒤). deny 규칙은 `UserRuleDeny`, ask 규칙은 `UserRuleAsk`, 한도는 `CeilingViolation` 이유를 그대로 낸다. 기억된 권한 저장소를 읽을 수 없을 때의 "묻기"(`RememberedStoreUnavailable`)도 같은 조건의 `browser_act`에는 질문 없이 거절이며 이유는 그대로 둔다(`store_unavailable_decision`). classifier 심사 뒤 digest 고정은 이미 거절인 판정을 덮어쓰지 않는다.
- **입력 연쇄의 검증 순서(독립 검토 5차 지적):** 검증과 정리 명령에서 난 오류는 종류를 지킨다. 문서를 닫는 오류(file chooser·download, 허용되지 않는 이동, detach, 전송 오류)는 `confirm_document`나 `releaseObject` 같은 뒤따르는 명령에서 나더라도 그대로 올라가고(`with_cleanup`: 치명 오류가 회복 가능한 `browser_stale_revision`을 이긴다), 이미 닫힌 문서의 `poll`도 `browser_document_changed`다. 요청 도중 target이 바뀐 `Page.getFrameTree`는 문서가 아니라 판정이 낡은 것이므로 `browser_stale_revision`이고 새 target은 닫지 않는다. `type`은 `DOM.focus` 뒤, 글을 넣기 직전, Enter 직전, Enter의 keyDown 뒤에 승인한 요소가 그 문서의 활성 요소(shadow root 포함)인지 확인한다(`focus_on_node`). 다른 frame으로 focus가 옮겨가면 Chromium이 이전 문서의 활성 요소를 되돌리므로 이 확인에 드러난다. 번호를 쓰는 `scroll`도 관찰이라 판정 문서를 끝까지 유지하고, node를 resolve한 뒤 scroll 함수를 보내기 직전에 지금 문서를 다시 읽는다. `click`은 binding 재확인 뒤 hit-test를 `mousePressed` 직전의 마지막 요청으로 보내고, `mousePressed` 뒤 binding 재확인과 함께 같은 지점을 다시 hit-test해 승인한 요소(또는 자손, 같은 frame)가 아니면 release 없이 브라우저를 끝낸다. 키: Enter·Backspace·Delete만 keyDown 뒤 시작 focus까지 엄격히 비교한다. Tab·Shift+Tab·방향키·Home·End·PageUp·PageDown·Escape는 focus 이동이 의도한 결과이므로 새 focus를 받아들이고, 시작 요소의 역할·이름·form·submitter와 문서가 같을 때만 keyUp까지 보낸다(아니면 끝낸다). Enter의 keyDown으로 승인한 제출이 이미 커밋돼 문서가 바뀌었으면 keyUp을 보내지 않고(아무도 승인하지 않은 문서에 입력하지 않는다) 연쇄를 끝내며 결과 읽기는 도착한 문서를 보인다. 상태 기록: 상태 파일을 쓰지 못하면(`browser_state_unavailable`) generation을 유지하지 않고 버린 뒤 메모리 상태를 `Failed`로 둔다(`publish_or_dispose`); 이미 버린 뒤의 기록 실패는 원래 오류를 우선한다. 문서 계층의 FIFO 밖에서 처리되는 이벤트는 둘뿐이다: `CdpDocument::initialize`가 target을 붙이기 전 받은 응답의 이벤트(아직 문서가 없다)와 종료 `close()`의 `Target.closeTarget` 응답(문서는 이미 닫혔다). 그 밖의 모든 이벤트는 inbox를 지난다.
- **입력 직전의 epoch 보호(독립 검토 6차 지적):** `CdpDocument`는 문서·target을 바꾸는 이벤트(`Page.frameNavigated`, `Page.navigatedWithinDocument`, `Target.attachedToTarget`, `Target.detachedFromTarget`)를 적용할 때마다 `epoch`를 올린다. 입력 단계는 확인을 시작하기 전에 epoch를 적고, 모든 `Input.*`(과 `type`을 시작하는 `DOM.focus`)은 `dispatch_input`으로만 보낸다: 문서가 닫혔거나 epoch가 바뀌었으면 보내지 않는다(첫 입력 전이면 `browser_stale_revision`, 그 뒤면 브라우저를 끝낸다). 그래서 확인 결과를 낸 응답 뒤의 정리 명령(`Runtime.releaseObject`, `DOM.describeNode`) 응답에 실린 이동·target 이벤트도 입력을 막는다. hit-test는 대상 subtree를 먼저 읽고 `DOM.getNodeForLocation`을 마지막 요청으로 둔다. 눌린 뒤의 확인(binding 재확인과 같은 지점의 hit-test)은 하나로 묶어 어떤 오류든(회복 가능한 오류는 종료로, 치명 오류는 그대로) release를 보내지 않는다. 키: Tab·Shift+Tab만 keyDown 뒤 focus 이동을 받고, 그때 실제 deep focus를 다시 읽어 검증한 문서 트리 안(http(s) frame)에 놓일 때만 keyUp을 보낸다(해석할 수 없는 iframe·다른 target이면 끝낸다). 방향키·Escape·Home·End·PageUp·PageDown·Backspace·Delete·Enter는 시작 focus까지 엄격히 비교한다. `type`의 focus 확인은 요소에서 위로 올라가는 검사(`getRootNode().activeElement === node`, host를 따라 document까지)라 닫힌 shadow root 안의 입력도 맞게 보며, 창 focus(`document.hasFocus()`)는 보지 않는다(Xvfb 창의 활성 상태와 무관하게 입력 대상만 묻는다). 오류 분류: node 명령(`DOM.resolveNode`·`DOM.describeNode`·`DOM.focus`·`Accessibility.getPartialAXTree`)의 서버 오류(-32000) 중 Chromium 6e148db의 node 부재 메시지(`STALE_NODE_MESSAGES`)만 `browser_stale_revision`이고 나머지는 `browser_protocol`이다. 회복 가능한 오류 응답 앞에 도착한 이벤트는 오류를 돌려주기 전에 먼저 적용해 chooser·detach가 결과가 된다(치명 오류는 그대로 generation을 끝내며, 실패한 admission이 남긴 부착 이벤트를 다시 처리하지 않는다). 상태 기록은 generation이 살아 있는 모든 자리(실행 뒤, 설치 뒤, maintenance의 viewer 실패, 다른 session의 busy)에서 `publish_or_dispose`를 쓴다.
- **입력 직전 확인의 마무리(독립 검토 7차 지적):** 문서 변경 판정은 전송 계층과 문서 계층이 같은 함수(`changes_document`)를 쓴다. 주 frame 이동뿐 아니라 `Page.frameDetached`, `Target.targetDestroyed`, `Target.targetInfoChanged`, chooser·download도 dispatch epoch를 올리고 번호 snapshot을 버린다(`frame_removal_in_the_final_hit_test_blocks_the_press_and_the_release`). focus 확인(`FOCUSED_HERE`)은 `focus_then_dispatch`로 보낸다: node를 resolve해 predicate를 묻고, 그 remote object를 살려 둔 채 바로 입력을 보내고, 그 뒤에 release한다. 그래서 predicate와 `Input.insertText`·`keyDown`·`keyUp` 사이에는 다른 요청이 없다(`focus_predicate_is_the_last_request_before_each_input`). 키의 predicate 대상은 `type`의 Enter면 글을 넣은 요소, 그 밖의 press는 승인한 focus node이고, Tab·Shift+Tab의 keyUp은 keyDown 뒤 다시 읽은 실제 deep focus의 node다. 그 destination은 구체적인 node여야 하며(focus된 요소가 없거나 frame owner·다른 target·검증되지 않은 frame이면 없다) 없으면 keyUp 없이 끝낸다. deep focus 해석은 `iframe`뿐 아니라 모든 frame owner(`frame`·`fencedframe`, Chromium이 `frameId`·`contentDocument`를 붙인 `object`·`embed` 등)를 자식 문서로 풀어야 하는 것으로 본다. 자식 문서가 허용된 http(s) 문서가 아니면(frameset의 `about:blank` frame 등) focus는 `{"unresolved":true}`로 기록되어 `look`은 성공하되 어떤 `press`도 준비되지 않고(`browser_stale_revision`), 그 focus로 재확인되는 키는 끝난다(`retained_active_element_binds_press_on_an_unfocused_page`, `focus_moving_keys_complete_while_committing_keys_stay_strict`). `DOM.getBoxModel`의 오류는 Chromium 6e148db의 "Could not compute box model."만 요소 생략(`browser_geometry_unavailable`)이고 node 부재 메시지는 `browser_stale_revision`, 그 밖은 `browser_protocol`이다.
- **키의 수신자는 창의 활성 상태와 무관(독립 검토 8차 지적):** deep focus(`DEEP_FOCUS`)는 `document.hasFocus()`를 묻지 않고 문서가 유지하는 `activeElement`를 shadow root·frame을 따라 푼다. Chromium 6e148db는 주입한 키를 전달하기 전에 페이지 focus를 복원하므로(`InputHandler` → `RenderWidgetHostImpl::Focus` → `SetPageFocus(true)`), 창이 비활성이어도 유지된 입력 칸·제출 버튼이 그 키를 받는다. 그래서 그 요소와 form이 승인 설명에 들어가고(`retained_active_element_binds_press_on_an_unfocused_page`) focus predicate(`FOCUSED_HERE`, shadow root 후보 판정도 `hasFocus()`를 보지 않는다)가 keyDown·keyUp을 지킨다. `body`·`documentElement` 밖에 활성 요소가 없는 문서만 수신자 없는 press(바인딩 없음)로 남고, 수신자가 frame owner 등으로 풀리지 않으면 `unresolved`로 기록되어 어떤 입력도 보내기 전에 press를 거절한다.
- **입력 수신자 확인은 Blink의 focused element로(독립 검토 9·10차 지적):** 입력 직전의 focus 확인은 JS로 `activeElement`를 되짚는 방식(retargeting 때문에 shadow host와 그 안쪽 control을 구별하지 못하고, 증인 요소를 옮기거나 비어 있던 닫힌 root에 요소를 넣는 페이지에 뚫린다)을 버리고, 접근성 트리의 `focused` 속성 하나로 한다(`CdpDocument::ax_focused`). Chromium 6e148db에서 `AXNodeObject::IsFocused`(ax_node_object.cc:3310–3323)는 `Document::FocusedElement()`(retargeting 없는 실제 focus 요소)와 node를 비교하고 창의 활성 상태는 보지 않는다. inspector는 이 값이 참일 때만 unignored node의 properties에 `focused`를 넣는다(inspector_type_builder_helper.cc `FillGlobalStates` 363–367, `BuildProtocolAXNodeForUnignoredAXObject` 865–878; ignored node는 826–860에서 properties 없음). 그래서 shadow host 안의 control이 focus를 가지면(닫힌 root 포함) host의 `focused`는 없고 안쪽 control에만 있다. guard는 `Accessibility.getPartialAXTree {backendNodeId, fetchRelatives:false}` 한 요청을 `Input.insertText`·`keyDown`·`keyUp`(Tab destination 포함) 직전의 마지막 요청으로 보내고, 응답에서 그 node가 ignored가 아니고 `focused`가 참일 때만 입력한다. 속성이 없거나 node가 ignored·부재면 `browser_stale_revision`으로 닫는다(첫 입력 뒤면 브라우저를 끝낸다). 요청 하나뿐이라 pierce된 `DOM.describeNode`와 object group도 없다. 읽기 시점의 deep focus 서술(`DEEP_FOCUS`·`shadow_focus`)은 설명을 만들 뿐이고 실행을 허락하는 것은 이 guard다. 가짜 peer는 Chromium 의미대로 문서의 focus 요소 하나를 두고 그 node에만 `focused`를 내며 창 활성 상태를 보지 않는다(`shadow_host_guard_requires_the_deepest_recipient`: 설명된 안쪽 요소로 focus 이동, 비어 있던 닫힌 root에 생긴 요소로 focus 이동 모두 Enter 없음; 닫힌 root 안의 승인 요소와 안쪽 focus가 없는 host는 통과).
- **frame owner는 입력 대상이 아니다(독립 검토 11차 지적):** 번호가 붙은 요소가 자식 browsing context를 가진 owner(`iframe`·`frame`·`fencedframe`·`portal`, 또는 `frameId`·`contentDocument`가 있는 `object`·`embed`)이면 `click`·`type`은 `DOM.focus`나 어떤 `Input.*`보다 앞서 `browser_input_denied`로 거절한다(`CdpDocument::frame_owner_target`, `DOM.describeNode` 한 번). Chromium 6e148db에서 그런 요소를 focus하면 부모 문서의 focused element는 owner가 되고(document.cc:6107–6120) 페이지 focus는 자식 frame으로 가므로(html_frame_element_base.cc:241–250) AX `focused`는 owner에 참이지만 Enter는 자식 문서로 간다. 자식 문서 안의 control은 자기 번호로 그대로 쓴다. press의 focus 해석은 이미 owner를 subject로 받지 않는다(`numbered_frame_owner_is_never_an_input_target`).
- **domain 규칙의 subject:** `open`은 요청 URL의 host, 다른 동작은 준비된 설명의 `origin` host다(`permission_materials.rs`). 문서가 없는 `close`는 host가 없어 domain 규칙에 맞지 않는다. parser는 `browser`에만 `domain:`을 더 받고 matcher는 selector로 tool을 확인하므로 `web_fetch`와 교차 적용되지 않는다.
- **production ceiling:** `runtime_capability_ceiling_from_registry`의 `browser` 분기가 `net_outbound`와 `browser_act`를 함께 낸다. 저장된 net-only ceiling은 바꾸지 않으므로 그런 하위 실행의 조작은 `CeilingViolation`으로 거절된다.

## 남은 제한

- 요소 이름과 form 이름은 사이트가 정한다. 이름이 효과를 정직하게 설명한다는 보장은 없다.
- 캡처 안의 글은 결과 검사에 들어가지 않는다. 검사 경고가 실행 후 결과를 없애지는 않는다.
- auto에서는 변경 동작마다 classifier 지연이 생기고 default에서는 각 동작에 질문할 수 있다.
- 입력 수신자 확인은 접근성 트리에 기대므로 접근성 객체가 없거나 ignored로 남는 요소에는 `focused`가 나오지 않아 그 요소에 대한 `type`·`press`는 실행되지 않는다(fail closed). focus된 요소를 가리는 잘못된 `aria-hidden`은 Chromium이 무시하므로(ax_object_cache_impl.cc:1108–1128, `EnsureFocusedObject`) 그런 입력 칸이 늘 거절되는 것은 아니다.
- 마지막 확인 응답과 입력 이벤트 사이에는 CDP 왕복 한 번만큼의 틈이 남는다. 그 사이에 페이지 script가 요소를 옮기거나 form을 바꾸면 그 입력은 확인하지 않은 상태에 닿는다. 확인을 입력 직전의 마지막 요청으로 두어 틈을 최소로 할 뿐 없애지는 못한다(PRD 020 남은 제한과 같다).
- mousedown에서 새 창을 여는 페이지는 `mousePressed` 응답에 target 부착이 실려 epoch가 바뀌므로 release를 보내지 않고 브라우저를 끝낸다. 문서가 바뀐 뒤의 입력은 어느 것도 보내지 않는다는 규칙의 대가다.
- 입력 연쇄의 첫 이벤트(mousedown, keydown과 그 keypress)는 보낸 뒤 되돌릴 수 없다. 그 뒤의 재확인이 실패하면 브라우저를 끝내는 것으로 더 나아가지 않을 뿐이며, 페이지가 첫 이벤트에 걸어 둔 동작은 이미 일어난 뒤다.
- 페이지가 연 popup은 현재 탭이 되고, 그 자신의 http(s) 문서가 identity가 된 뒤에야 판정 subject가 된다. `about:blank`에 머무는 popup은 `look`할 것이 없어 `open`이 필요하다.
