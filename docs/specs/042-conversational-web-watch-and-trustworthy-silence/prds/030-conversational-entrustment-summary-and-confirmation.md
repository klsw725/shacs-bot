# PRD 030. 대화형 위임 요약과 확인

Status: Complete (Scoped)

Depends on: [PRD 000](000-web-page-observation-and-condition-decision.md), [PRD 010](010-change-failure-recovery-and-gap-notification.md), [PRD 020](020-decision-deadline-reminder.md) 완료. 뒤 번호 PRD에는 의존하지 않는다.

## Goal

사용자가 대화로 맡기면 어시스턴트가 **무엇을, 어디서, 어떤 조건으로 살피고 어떻게 알릴지** 요약해 보여주고, 사용자가 확인한 것만 위임·관측·알림 설정·마감으로 한 번에 설정한다. 이 PRD가 [042 SPEC](../SPEC.md) 전체의 실제 사용자 흐름을 닫는다.

## Scope

1. **요약 만들기:** 대화 요청이나 어시스턴트의 제안에서 URL, 볼 값(PRD 000 등록 후보의 지금 값과 위치), 구체 조건, 확인 주기, 알림 대상, 실패 알림 기준 시간, 선택적인 결정 마감과 알림 시점을 담은 요약을 만든다. 막연한 바람은 지원 조건 종류로 바꿔 제안한다. 지원하지 않는 조건·URL·알림 대상, 볼 값을 찾을 수 없는 페이지는 이유와 대안을 요약에 표시한다. 페이지 내용은 PRD 000의 등록 후보 단계로만 읽으며 요약의 URL·조건·주기·알림 대상을 바꾸지 못한다.
2. **확인 결속:** 요약은 고유 ID와 revision을 가지며 원래 session·channel·chat·발신자에 결속된다. 확인은 같은 발신자의 것만 인정하며 두 가지뿐이다. (1) 그 요약이 어시스턴트의 가장 최근 응답이고 대화에 대기 중인 요약이 그것 하나일 때 보낸 정해진 확인 응답("응", "네", "맞아", "그렇게 해" 등 사용자 문서에 적은 목록). (2) 현재 요약 ID와 revision을 담은 지원 채널의 버튼. 가장 최근·유일 조건은 (1)에만 적용한다. 다른 요약 표시나 재시작으로 닫힌 요약과 이전 ID·revision은 어느 방식으로도 인정하지 않는다. 그 밖의 응답은 위임을 만들지 않고 다시 묻는다. 무응답, 다른 요약 표시, 재시작은 대기 중인 요약을 닫는다.
3. **일괄 설정:** 새 위임이 확인되면 PRD 000의 첫 기준 절차로 값을 다시 읽는다. 보여준 값과 다르면 바뀐 요약을 새 revision으로 다시 보여주고 확인을 받는다. 같으면 036 위임(동의 근거: 요약 확인), PRD 000 관측과 첫 기준, PRD 010 알림 설정, PRD 020 마감을 한 번에 설정한다. 일부만 설정된 상태를 남기지 않는다.
4. **대화로 조회·수정:** "마지막으로 언제 확인했어?" 같은 질문에 PRD 000·010의 상태 사실로 답한다. 조건·URL·알림 대상·마감 변경은 새 요약 확인을 거친다. 확인된 변경이 URL·추출 기준·조건·주기를 바꾸면 첫 기준 절차를 다시 거치고, 알림 대상·기준 시간·마감만 바꾸면 해당 revision만 올리고 비교 기준을 유지한다. pause/resume/done/clear는 036 명령이나 확인을 거친 대화 요청으로 처리하며, 그 뒤 기준 처리는 036과 PRD 000을 따른다.

## Non Scope

- 사용자 자료를 훑어 요청하지 않은 일을 제안하는 기능, 여러 페이지 위임.
- 036 `/work` 명령과 `propose_entrusted_work` 제안의 의미 변경. 그 제안에서 일반 `yes`를 동의로 보지 않는 규칙은 그대로다.
- 예약·구매·발송 승인. 036의 별도 결정 경계를 유지한다.

## Parent Requirement Mapping

- [042 SPEC](../SPEC.md)의 소유 범위 1·8과 수용 조건 1·7을 소유한다.

## Required Contract

1. 확인 전에는 위임·관측·알림 설정·마감·wake가 없다. 일회성 질문 뒤에는 활성 위임이 없다.
2. 확인 판정을 모델의 추측에 맡기지 않는다. 판정이 불분명하면 만들지 않는다.
3. 위임 확인은 tool permission grant나 예약·구매·발송 승인이 아니다.
4. 요약에 표시한 값(URL·볼 값·조건·주기·알림 대상·기준 시간·마감)과 저장된 값이 같다.

## Acceptance Criteria

1. 실제 대화 진입점(agent REPL 또는 지원 channel), `127.0.0.1/32`만 허용한 시험용 profile의 로컬 HTTP 서버, 로컬 SMTP, 시험용 시계로 요청 → 요약 → 확인 → A/A/무관/B → 변화 알림 한 건, 확인 실패 → 실패·회복 알림, 마감 알림을 끝까지 실행한다.
2. 일회성 질문, 애매한 응답, 다른 발신자의 확인(버튼 포함), 바뀐 요약에 대한 이전 확인, 가장 최근 응답이 아닌 요약에 대한 확인 응답, 새 요약 표시로 닫힌 요약이나 이전 ID·revision을 담은 버튼, 재시작 뒤의 확인에서 위임이 생기지 않는다. 요약과 확인 사이에 값이 바뀌면 다시 확인을 요구한다.
3. 지원하지 않는 조건이나 알림 대상, 볼 값을 찾을 수 없는 페이지는 요약 단계에서 이유와 함께 안내되고 위임이 생기지 않는다. 페이지에 넣은 지시 문구가 요약 내용을 바꾸지 않는다.
4. 대화에서 마지막 성공 확인 시각과 현재 상태를 물으면 저장된 사실과 같은 답을 받는다. 조건 변경은 새 요약 확인 뒤에만 적용되고, 알림 대상이나 마감만 바꾸면 비교 기준이 유지된다.

## Closure Evidence

1. 실제 대화 transcript, 저장 상태, 수신 메일을 연결한 end-to-end 기록.
2. 확인 결속·애매한 응답·다른 발신자·재시작·일괄 설정 원자성·페이지 지시 문구 테스트.
3. 사용자 문서에 대화형 위임 사용법, 확인 응답 목록, 비보장 범위를 기록.

PRD 030은 앞 PRD에서 닫힌 관측·알림·마감 결과만 소비한다. 자체 요약·확인 조건과 실제 end-to-end 흐름을 충족하면 뒤 PRD 없이 종료한다.

## 구현 메모 (2026-10-26)

- **제안과 요약:** 모델은 읽기 전용 도구 `propose_web_watch`로 제안만 한다(만들거나 권한을 주지 않음). turn이 끝나면 런타임이 마지막 제안을 결정적으로 검사해 요약을 만든다. 같은 turn에서 `propose_web_watch`·`web_watch_status` 말고 다른 도구(페이지 읽기·검색·파일·MCP 등)가 쓰였으면 그 결과가 조건이나 주기를 바꿨을 수 있으므로 제안을 쓰지 않고 이유만 보인다. turn은 사용자가 보낸 마지막 메시지(runtime이 `owner_turn` 표시를 붙인 user 메시지)부터 끝까지이며, 권한 질문에 승인해 이어 실행한 도구와 `ask_user` 질문(또는 `/action accept`)의 답으로 이어진 부분을 포함한다(`ask_user` 답은 사용자의 말이므로 다른 도구로 보지 않는다). 제안은 이번 turn의 기록에서 찾는다. 새 메시지면 그 메시지를 처리하며 더해진 기록(실행의 새 메시지)이고, 질문의 답이나 승인으로 이어진 메시지면 마지막으로 turn을 끝낸 답 바로 뒤부터다. 그래서 제안한 뒤 `ask_user`나 권한 질문을 한 turn은 질문을 먼저 보이고 답으로 이어진 turn이 끝날 때 요약(또는 거절 이유)을 보이며, 도구마다 승인을 묻는 모드(Auto)에서 사용자가 승인한 `propose_web_watch`도 요약이 된다(승인은 제안 도구의 실행만 허락하고, 설정은 요약 확인 뒤에만 한다). 승인한 다른 도구의 결과는 위의 turn 검사가 다른 내용으로 잡는다. 모델이 `message` 도구로 답을 따로 보낸 turn의 제안도 다른 도구를 쓴 turn이므로 거절 이유를 그 메시지들 뒤에 보낸다(기다리던 요약은 닫히고, 그 turn에서 다시 묻지 않는다). 사용자가 보내지 않은 turn(하위 작업 결과·예약·자동화·goal 계속처럼 runtime이 user 역할로 넣은 메시지)의 제안은 쓰지 않는다. 질문의 답이나 승인으로 이어진 turn의 제안은 그 turn을 보낸 사용자가 혼자 이어 갔을 때만 쓰고, 같은 대화방의 다른 발신자가 한 번이라도 답했으면 이유를 보이고 쓰지 않는다(`ask_user` 질문에는 런타임 규칙대로 대화의 누구나 답할 수 있다). 이를 위해 turn이 사용자를 기다리며 멈출 때 그 turn을 보낸 발신자를 session metadata(`web_watch_turn_owner`: turn 첫 메시지의 digest와 session·channel·chat·발신자)에 적고, 다른 발신자가 이어 가면 지우며, turn이 끝나면 지운다. 페이지 주소와 메일 주소는 사용자가 직접 보낸 메시지(이번 메시지와 `owner_turn` 표시가 있는 이전 메시지)에 쓴 온전한 주소여야 하고(페이지 내용이나 하위 작업 결과가 주소를 넣을 수 없고, 쓴 주소의 앞이나 뒤만 잘라 쓸 수 없음), 주소·볼 값·조건·주기(기본 1시간)·Email 대상과 Email 채널·실패 기준 시간·마감은 CLI/API와 같은 규칙으로 검사한다. 페이지는 PRD 000 등록 후보 단계로만 한 번 읽어 첫 후보의 지금 값과 위치를 보여주며(위치는 확인 뒤 저장될 추출 기준이 읽는 곳이라, 같은 앞뒤 문구가 여러 곳이면 그중 몇 번째인지를 후보 목록의 10개 제한과 관계없이 보인다), `below_current`·`above_current`는 지금 값의 마지막 자리 한 단위로 바꾼다. 문제가 있으면 이유와 대안만 보여주고 대기 상태를 남기지 않는다. 요약은 결정적인 영어 문장이며 사용자·페이지 문구는 `safe_text`, 주소는 query·fragment 없이 보여준다(가려진 query가 있으면 그렇다고 적는다). 목표(`goal_text`)는 `safe_text`로 다듬은 값이 요약에 보이고 그 값 그대로 위임 목표로 저장된다. 요약 상태(`pending_web_watch_summary`)는 session에 하나만 두고 요약 ID·revision·process epoch·session·channel·chat·발신자·표시 시각·만료(30분)·보여준 메시지 위치·후보 token·검사한 설정을 담는다. 새 요약이나 거절된 요약 표시는 이전 요약을 닫는다. 버튼 채널에는 `/watch confirm <id> <rev>`, `/watch cancel <id>` 버튼을 붙인다. 요약은 그 turn의 마지막 assistant 메시지가 되며, 도구 호출이 든 메시지는 건드리지 않는다. channel runtime은 042 대화 답(요약 포함) 뒤에 session의 workflow 상태 메시지를 붙이지 않는다(036 알림과 같은 규칙).
- **확인 판정:** provider 호출 전에 결정적으로 한다(권한 wizard 다음, method/workflow 앞). 버튼(또는 같은 명령)은 같은 session·channel·chat·발신자, 현재 ID·revision, 열린 요약(같은 epoch, 만료 전)일 때만, 목록의 확인 답은 여기에 더해 요약이 가장 최근 assistant 메시지일 때만 인정한다. 다른 발신자·이전 ID나 revision·잘못된 명령은 아무것도 만들지 않고 요약을 다시 보여주어 가장 최근 메시지로 둔다. `/watch` 명령(버튼)은 다른 질문의 처리(036 행동 결정, 권한 wizard)보다 먼저 판정한다. 다른 질문(`ask_user`·행동 질문·권한 승인)이 답을 기다리는 동안에는 그 질문의 열린 도구 호출이 다음 답을 받도록 이 명령과 답을 대화 기록에 넣지 않고, 그때 보인 요약은 최근이 아님으로 둔다. 일반 확인·취소 답은 그 질문의 답으로 남는다. 요약 뒤에 다른 응답이 실제로 나갔으면(명령 응답(다른 turn 중에 답해 저장되지 않은 priority 명령 포함), `ask_user`·권한 질문 같은 interrupt, `message` 도구 전송, 이미지·복합 요청의 답, provider 오류 답, 그 대화로 보낸 036·042 알림) 요약을 "최근 아님"으로 낮추고, 그 뒤의 확인 답과 취소 답은 평소 turn으로 넘겨 그 응답의 답이 되게 한다(버튼과 `/watch cancel`은 계속 유효). turn 끝의 후처리가 보낼 답을 바꿔 요약이 빠지면(비정상 상태의 action 질문 정리 등) 요약을 낮추고 응답으로 세며 버튼을 떼어, 실제로 보낸 답에 요약이 들어 있을 때만 보여준 것으로 본다. 이를 위해 이 프로세스가 (workspace 경로, session)마다 보낸 "요약이 아닌 응답"의 수를 세고(재시작하면 요약도 닫히므로 프로세스 안에서만 셈. workflow 완료·차단·실패 답도 세고, 알림은 실제로 전송 queue에 들어갔을 때만 센다), 요약은 보여질 때의 수를 기억해 일반 확인은 그 수가 그대로이고 요약이 session 기록의 마지막 assistant 메시지일 때만 인정한다. 닫힌 요약(재시작·만료)은 이유를 알리고 지우며, `/new`도 요약을 지운다. 그 밖의 답은 평소 turn으로 넘기고, 같은 발신자의 요약이 아직 열려 있으면 답 끝에 다시 묻는다.
- **일괄 설정:** 확인하면 후보 token으로 페이지를 다시 읽는다. 값이 다르면 그 값을 담은 다음 revision을 보여준다. 같으면 turn이 이미 잡은 session 잠금 안에서 session 복사본에 036 위임(동의 `confirmed_proposal`, 근거 `web-watch-summary:<id>:<rev>`), PRD 000 계획과 첫 기준, PRD 010 알림 설정, PRD 020 마감을 차례로 적용하고, 모두 성공했을 때만 원본을 바꿔 응답과 함께 한 번 fsync로 저장한다. 하나라도 실패하면 아무것도 남기지 않고 요약을 닫는다. 036 위임의 지시문(`conditions.instructions`)에는 바뀔 수 있는 설정(주소·볼 값·조건·주기·알림·마감)을 넣지 않고 web watch 설정을 가리키는 고정 문장만 두므로, 확인된 변경 뒤에도 `/work read`가 예전 값을 말하지 않는다. 이를 위해 036 생성, PRD 000 확인(읽기/저장 분리), PRD 010·020 설정 검사를 저장하지 않는 함수로 나눴고 공개 CLI/API는 그대로다.
- **조회와 변경:** 읽기 전용 도구 `web_watch_status`를 부르면 런타임이 모델의 답 대신 `web-status`와 같은 저장된 사실(마지막 성공 확인 시각과 그 확인의 값, 마지막 판정과 이유 코드, 실패 구간, 다음 확인, 대상, 마감)을 문장으로 답한다. 요청은 이번 메시지를 처리하며 더해진 기록(실행의 새 메시지와, 승인으로 이어졌다면 승인한 도구의 결과)에서 찾으므로 사용자가 승인해 실행된 호출도 답한다. 같은 turn에 제안도 있으면 저장된 사실을 앞에, 요약(또는 거절 이유)을 마지막에 둔다(요약이 마지막 메시지로 남아 일반 확인 답이 통한다). 그 turn이 모델의 마지막 답으로 끝나지 않아도 답한다: `message` 도구로 보냈으면 저장된 사실을 그 뒤 마지막 답으로 보내고(`message` 도구가 보낸 turn은 마지막 답을 보내지 않는 규칙의 예외), `ask_user`·권한 질문으로 끝났으면 저장된 사실을 그 질문 문장의 앞머리에 붙여 한 메시지로 보낸다(질문의 도구 호출이 열려 있으므로 기록에 따로 넣지 않고, turn의 결과 문장이 되어 로컬 API 응답에도 그대로 실린다). 웹 감시 도구 호출 뒤의 모델 요청이 실패해도(요청 오류로 끝나든 모델이 오류 응답(`finish_reason: error`)을 돌려주든) 같은 마무리를 거치고 웹 감시 답은 오류 문장 뒤에 붙는다. 요청 오류의 경우는 다음과 같다. 실행의 checkpoint가 알린 도구 결과를 모아 두므로(웹 감시 도구의 결과는 그대로, 다른 도구는 이름만), 제안은 요약이나 거절 이유가 되고 상태 요청은 저장된 사실로 답한다. 이 답은 오류 문장 뒤에 붙고(요약이 마지막이고 버튼도 붙음), 다른 도구가 쓰였으면 그 이름으로 알 수 있어 제안을 거절한다. 기존 위임 변경은 `work_id`와 바꿀 항목만 담은 제안으로 하며, 요약은 바뀌는 점과 비교 기준 유지 여부와 함께 새 요약처럼 볼 값의 위치와 지금 값을 보여준다. 위치는 저장된 추출 기준의 앞 문구(문구 조건은 앞뒤 문구, PRD 000 상태 출력처럼 안전하게 다듬은 것)와, 같은 문구가 여러 곳이면 몇 번째인지로 보인다. 페이지·볼 값·조건·주기를 바꾸면 확인에 쓸 읽기로 지금 값을 보이고, 메일 주소·실패 기준·마감만 바꾸면 저장된 기준으로 한 번 읽어 보여주기만 한다(확인 때 다시 읽지 않고 기준도 그대로다). 그때 페이지를 읽을 수 없으면 그 이유를 보이고 변경은 그대로 확인할 수 있다. 지금 값은 페이지에 보이는 표기(예: `₩12,900`)로도 보이며, 확인 순간 값이 바뀌어 다시 보이는 다음 revision도 그 순간 페이지의 표기를 보인다. 페이지·볼 값·조건·주기가 바뀌면 다시 읽어 확인 순간의 값이 새 기준이 되고(관측 revision +1), 메일 주소·실패 기준·마감만 바뀌면 해당 revision만 오르고 기준은 유지된다. 마감은 준 항목만 바뀐다. 주지 않은 마감 시각·알림 시점은 지금 값을 쓰므로 알림 시점만 바꿀 수 있고, 마감이 없는데 알림 시점만 주면(새 위임도 같다) 이유를 보인다. 마감 시각과 알림 시점이 지금과 같은 마감은 다르게 적었어도(다른 시간대 표기, 기본 알림 시점을 적어 넣음) 지금 마감 그대로라 바뀌지 않고, 즉시 알림(`remind_now`, 알림 시점이 이미 지났을 때만 고르는 것)도 그대로 남는다. 그 밖의 마감 변경은 제안이 준 즉시 알림 여부로 다시 검사한다. 알림 대상이 있으면 대상을 바꾸지 않는 변경도 요약 때와 확인 때 Email 채널이 보낼 수 있는지 PRD 010과 같은 규칙으로 확인한다. 주기만 바꾸면 저장된 실패 기준은 다시 검사하지 않고 두며, 실효 기준은 PRD 010대로 새 주기의 2배 이상으로 올라간다(대상도 함께 바꿔 다시 저장할 때는 그 실효 값을 저장). 상태 답의 값은 snapshot의 `last_read`(현재 계획의 마지막 성공 확인, 없으면 기준)로, 보관 기록 수와 관계없다. 확인 때 요약 시점의 관측·알림·마감 revision 세 개를 바꾸는 항목과 관계없이 모두 비교하므로 그사이 어느 하나라도 바뀌었으면 거절된다. pause/resume/done/clear는 036 `/work` 명령으로 한다.
- **설정:** CLI의 agent loop 설정이 페이지 읽기(제품은 공개 주소만, 시험 profile은 `127.0.0.1/32` 허용), 읽기 한도, data dir, Email 채널 준비 여부를 넘긴다. `session export`(`mask_web_watch_session`)는 요약 상태의 후보 token을 빼고 그 주소의 query·fragment를 가리며, 대화 기록·끝나지 않은 turn의 checkpoint·대기 중인 승인 안의 웹 감시 도구(`propose_web_watch`·`web_watch_status`) 호출(호출 ID와 모델이 쓴 인자 이름 포함)과 결과에서도 모든 주소(scheme 없이 쓴 것 포함)를 scheme·host·path로 줄인다(줄인 이름이 겹치면 번호를 붙여 항목을 잃지 않는다). 그 밖의 내용은 `session export`의 원래 규칙대로(대화 메시지와 도구 payload를 담는 민감한 로컬 자료) 저장된 그대로이며, 사용자가 쓴 글과, 요약·알림 설정·상태 답처럼 알림 메일 주소를 보이는 곳도 그대로다. SDK 실행 결과의 `messages`도 같은 처리를 거친다.
- **진단 출력:** 도구 진행 이벤트(observability hook·SDK payload), provider 관찰 이벤트, `runtime --verbose` 로그에서 웹 감시 도구의 인자와 결과는 숫자·참거짓과 선택만 이름 짓는 필드(일반 단어로 쓴 `condition`·`work_id`, 숫자로 쓴 `condition_value`)만 남는다(`web_watch_status`는 `work_id` 하나만 받고, 결과에 되풀이한 `work_id`도 같다). 주소·메일·목표·표시 문구 같은 다른 문자열은 한 단어여도 정해졌다는 표시(`<set>`)로만 보이고, 도구가 받지 않는 필드는 빠진다. 오류 결과는 거절됐다는 사실만 남는다. core와 CLI가 `shacs_utils::progress_events`의 같은 projection을 쓴다. `--verbose`의 받은 메시지·모델 응답 미리보기도 주소(scheme 없이 쓴 것 포함)는 scheme·host·path만 보이고, 메일 주소와 다른 낱말은 그대로다(`without_url_details`). provider가 정한 도구 호출 ID가 평범한 토큰(영문자·숫자·`_`·`-`·`.`·`:`로 된 128자 이하)이 아니면 주소와 query를 담았을 수 있으므로, provider 관찰 이벤트, 도구 진행 이벤트(callback과 실행 결과의 `tool_events` 모두, Tool Search bridge(`tool_call`) 이벤트의 연결 근거 `mapping_evidence.bridge_call_id`와 detail 포함), 인자를 받지 않는 hook에 넘기는 호출과 응답, 권한 자동 승인 진단(분류기 근거의 `provider_tool_call_id`), 요약의 근거(`tool_call:<id>`), 실행 기록(`runtime_execution`)에는 그 ID 대신 그 SHA-256(`sha256:` 뒤 64자리 hex)이 쓰인다. `sha256:`으로 시작하는 평범한 ID도 같이 바꾸므로 평범한 ID가 다른 호출의 digest와 같아질 수 없고, 서로 다른 두 호출이 같은 이름을 갖지 않는다. 대화 기록에는 provider가 호출과 결과를 짝짓도록 원래 ID를 둔다. plugin hook(외부 명령과 plugin의 JavaScript·TypeScript `tool:before`)에는 호출 ID를 같은 digest로, 웹 감시 도구 호출의 인자를 진행 이벤트와 같은 projection으로 넘긴다(다른 도구의 인자는 plugin 정책이 판단하도록 그대로). plugin이 호출을 막은 기록(spec030 진단의 hook 거절 `call_ref`)에도 같은 digest가 남고, 막은 결과는 원래 ID로 호출에 짝지어진다. 인자를 받지 않는 hook이 digest로 본 호출을 막으면 그 막음은 원래 호출에 짝지어지고, 방식 기록(`/method status`)도 진행 이벤트의 digest로 호출과 결과를 짝짓는다.
- **streaming API:** 로컬 API의 streaming(SSE) 응답은 모델 스트림만 흘려보내므로, 런타임이 쓴 답인 웹 감시 답(요약·확인 결과·상태 답 등 stop reason이 `web_watch`로 시작)과 turn을 끝내는 질문(stop reason `ask_user`, 저장된 사실이 앞에 붙은 경우 포함)은 모델 스트림 뒤에 이어 보내고 그 stop reason으로 끝낸다. 그래서 SSE 사용자도 확인 전에 요약을, 답해야 할 질문과 그 앞의 저장된 사실을 본다.
