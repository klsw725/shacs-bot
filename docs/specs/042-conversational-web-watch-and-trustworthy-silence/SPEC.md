# 042. 대화로 맡긴 웹페이지 관찰과 믿을 수 있는 침묵 아키텍처 명세

Status: Complete (Scoped)

Consumes: 010 host safety, 029 durable runtime, 030 trusted execution, 031 execution snapshot, 033 goal and automation, 036 entrusted work

## 목적과 완료 경계

이 스펙은 [`intent.md`](../../../intent.md)의 첫 경험을 사용자가 실제로 맡길 수 있는 첫 대상으로 넓힌다. 사용자가 대화로 맡긴 **공개 웹페이지 한 곳의 값 하나**를 어시스턴트가 직접 확인하고, 사용자와 함께 정한 조건에 비추어 의미 있는 변화가 있거나 꼭 알아야 할 때(사용자가 정한 결정 마감, 기준 시간을 넘은 확인 실패와 그 회복, 어시스턴트가 꺼져 있던 공백)만 먼저 알린다. 알림이 없다면 **요약에 표시한 기준 시간을 넘는 확인 공백 없이 확인했고 의미 있는 변화도 없었다**는 뜻이어야 한다.

[036](../036-entrusted-work-continuity-and-change-notification/SPEC.md)은 명시 명령 위임, 사용자 소유 로컬 정수 JSON 관측, 정수 상한 비교와 Email 통지를 scoped 완료했다. 그러나 관측 자료를 사용자나 다른 프로그램이 만들어야 하고, 읽기 실패 뒤에는 다음 확인을 멈추고 알리지 않으며, 결정 마감 알림이 없다. 042는 036의 완료 판정과 기존 명령·로컬 파일 관측의 의미를 다시 열지 않고, 036이 소유한 위임·동의 근거·관측/판정/통지 사실과 외부 행동 결정 경계를 소비해 이 차이를 메운다.

이 스펙은 [037](../037-task-specific-assistant-methods/SPEC.md)의 전문 방식이나 [038](../038-evidence-backed-method-learning/SPEC.md)의 방법 학습 없이 단독으로 종료할 수 있어야 한다. 어시스턴트는 계속 켜 두는 곳(예: Docker Compose의 `shacs-gateway`)에서 실행된다고 전제하되, 꺼져 있던 공백을 숨기지 않는다.

## 소유 범위

1. **대화형 위임 요약과 확인:** 사용자가 대화에서 일을 맡기거나 어시스턴트의 제안에 동의하면, 어시스턴트는 볼 곳, 볼 값과 지금 값, 구체 조건, 확인 주기, 알림 대상, 실패 알림 기준 시간, 선택적인 결정 마감과 알림 시점을 담은 요약을 보여준다. 어시스턴트가 먼저 제안할 때도 같은 요약으로 제안한다. "싸지면"처럼 막연한 바람은 지원 조건 종류 중 하나의 구체 조건으로 바꿔 제안하고, 지원하지 않는 조건·URL·알림 대상은 이유와 대안을 보여준다. 위임과 관측은 같은 대화·같은 발신자의 확인으로만 만든다. 확인으로 인정하는 것은 (a) 그 요약이 어시스턴트의 가장 최근 응답이고 유일한 대기 요약일 때 보낸 정해진 확인 응답과 (b) 현재 요약 ID·revision을 담은 지원 채널의 버튼뿐이며, 가장 최근·유일 조건은 (a)에만 적용한다. 다른 요약 표시나 재시작으로 닫힌 요약과 이전 ID·revision은 어느 방식으로도 인정하지 않는다. 그 밖의 응답, 애매한 응답, 무응답·거절은 아무것도 만들지 않고 필요하면 다시 묻는다. 036의 `/work` 명령과 `propose_entrusted_work` 제안의 의미(일반 `yes`는 동의가 아님)는 그대로다.
2. **웹페이지 관찰:** 등록 때 페이지를 실제로 읽어 볼 값과 위치를 보여주고, 사용자가 확인한 추출 기준을 저장한다. 확인하는 순간 같은 기준으로 다시 읽은 값이 보여준 값과 같을 때만 그 결과를 첫 기준으로 저장하고, 다르면 다시 확인받는다. 주기 확인은 provider·agent turn·범용 도구 없이 저장된 기준으로만 값을 읽는다. 기준으로 값을 찾지 못하거나 해석이 모호하면 추측하지 않는다. 관측마다 읽은 시각과 결과·실패 분류를 남기고, 응답을 받은 경우에만 최종 URL·HTTP 상태·내용 digest·추출 값을 남긴다. 응답 본문과 주변 문구는 영속 저장하지 않는다. 페이지 내용은 지시가 아니라 자료로 다룬다.
3. **조건과 판정:** 지원 조건 종류는 숫자 값의 상한·하한과 확인한 문구의 나타남·사라짐이다. 036의 기준·무변화·조건 무관 변화·조건 결과 변화·불확실 의미를 웹 관측에 적용한다. 조건 충족 여부가 바뀐 경우만 통지 후보이고, 추출 실패·모호한 값·형식이나 통화의 불일치는 `unknown`이며 기준을 갱신하지 않는다. 모델의 중요도 판단, 페이지 텍스트 diff, 확인 주기 도래는 통지 근거가 아니다. 생명주기 전이는 036 계약을 따르며, `resume`은 새 goal lineage를 시작하므로 다음 비교 가능한 관측을 새 기준으로 삼는다.
4. **계속 확인과 상태:** 확인에 실패해도 다음 확인을 멈추지 않는다. 어시스턴트가 꺼져 예정 확인이 밀린 기간은 실패가 아니라 공백으로 따로 기록하고, 다시 켜지면 밀린 확인을 바로 실행한다. 네트워크·HTTP·추출 실패와 goal·동의 gate의 `blocked`를 구분해 기록하고, 마지막 성공 확인 시각, 진행 중인 실패 구간, 다음 확인 시각을 CLI/API로 조회할 수 있게 한다.
5. **변화 알림과 전달:** 통지 후보를 036의 durable route와 Email 경로로 보낸다. 첫 알림 대상은 요약에서 확인한 단일 `email:<address>`이며 042가 위임과 별도로 저장한다. 036의 `linked_targets`를 발송 대상으로 재해석하거나 036 작업의 owner-Email 규칙을 바꾸지 않는다. 알림 종류를 구분해 렌더링하고 사건별로 중복과 오래된 알림을 막는다. 전달 실패와 `unknown`은 확인 성공·enqueue와 분리한다.
6. **확인 실패·회복·공백 알림:** 연속 실패 구간이 기준 시간 이상 이어지면 구간마다 한 번 알리고, 그 알림 뒤 첫 성공에서 한 번 회복을 알린다. 어시스턴트가 꺼져 있어 예정 확인이 기준 시간 이상 밀렸다면 다시 켜진 뒤 그 공백을 한 번 알린다. 공백은 실패 구간의 길이에 넣지 않는다. 확인 실패 중에는 변화 알림을 만들지 않는다.
7. **결정 마감 알림:** 사용자가 정한 결정 마감의 알림 시점에 변화가 없어도 한 번 알린다. 마감은 관측 조건과 따로 revision을 가지며 바꿔도 비교 기준이 다시 잡히지 않는다. 마감 변경·pause·done·clear 뒤에는 이전 마감 알림을 보내지 않고, resume 뒤에도 지난 알림을 소급해 보내지 않는다.
8. **대화로 조회·수정:** 대화에서 마지막 성공 확인 시각과 현재 상태를 물을 수 있다. 조건·URL·알림 대상·마감을 바꾸는 요청은 새 요약 확인을 거친다. URL·추출 기준·조건·주기를 바꾸면 기준을 다시 잡고, 알림 대상·기준 시간·마감만 바꾸면 기존 비교 기준을 유지한다.

## 반드시 지킬 것

- 확인받지 않은 요약이나 추측한 동의로 위임·관측을 시작하지 않는다. 확인은 요약 ID·revision·대화·발신자에 결속되고, 확인 판정을 모델의 추측에 맡기지 않는다.
- 값을 찾지 못하면 추측하지 않는다. 추출 실패는 변화도 무변화도 아니며, 기준 시간을 넘은 실패를 침묵으로 덮지 않는다.
- 등록 후보는 결정적 파서나 도구가 꺼진 구조화 단계에서 값·위치 후보로만 만든다. 페이지 문구는 요약의 URL·조건·주기·알림 대상을 바꾸거나 도구 실행을 일으킬 수 없다.
- URL userinfo, 로그인·cookie·인증 header·credential이 필요한 요청, JavaScript 실행, 접근 차단이나 이용 제한의 우회는 지원하지 않는다. 한 번의 확인에서 redirect 경로 하나만 요청하고 즉시 재시도하지 않으며, `Retry-After`와 429·503 backoff를 확인 주기보다 우선한다.
- production 웹 관찰은 `tools.ssrfWhitelist`와 관계없이 공개 주소만 허용한다. 로컬 주소 허용은 production 빌드에서 쓸 수 없는 종료 시험용 profile에만 둔다.
- 응답 본문과 주변 문구를 영속 저장하지 않는다. 관측 사실과 알림·조회·진단 출력에는 URL의 query·fragment를 남기거나 표시하지 않는다.
- 예약·구매·발송 같은 외부 확정 행동은 036의 별도 결정과 기존 도구 권한을 그대로 거친다. 위임 확인은 그 승인이 아니다.
- 여러 페이지 비교, 사이트별 전용 연동, 사용자 자료를 훑어 요청하지 않은 도움을 찾는 일, 모델 판단에 따른 통지, 모든 채널 parity, 원격 수신 ACK와 exactly-once 전달은 042의 완료 조건이 아니다.

## 수용 조건

1. 실제 대화 진입점에서 "이 페이지 가격 좀 봐줘, 싸지면 알려줘" 같은 요청에 요약이 표시되고, 같은 발신자가 현재 요약을 확인한 뒤에만 위임과 관측이 생긴다. 일회성 질문, 애매한 응답, 다른 발신자의 응답, 바뀐 요약에 대한 이전 확인, 재시작 뒤의 확인은 아무것도 만들지 않는다. 지원하지 않는 조건과 알림 대상은 요약 단계에서 이유와 함께 안내된다.
2. 제어 가능한 로컬 HTTP 서버의 페이지에서 미리보기 A를 확인하면 확인 순간 다시 읽은 A가 기준이 되고, 이후 확인의 A → 조건과 무관한 변화 → 조건 결과가 바뀐 B는 무변화·무변화·통지 후보로 남는다. 확인하는 순간 값이 바뀌었다면 다시 확인을 요구한다. 페이지에 넣은 지시 문구는 설정과 판정에 영향을 주지 않는다.
3. 내부 주소·사설 redirect·userinfo가 있는 URL은 설정에서 거절되고, 정적 내용에서 볼 값을 찾을 수 없는 페이지는 `static_content_unavailable`로 남으며 성공을 합성하지 않는다. 마지막 성공 확인 시각과 현재 상태를 CLI/API에서 조회할 수 있다.
4. 조건 2의 B만 이전/새 값·조건·URL·읽은 시각·근거가 담긴 알림으로 한 번 전달되고, 기준·무변화·무관 변화는 침묵한다.
5. 페이지를 기준 시간 넘게 읽을 수 없게 만들면 실패 알림이 한 번, 회복 뒤 회복 알림이 한 번 전달되고 실패 중에는 변화 알림이 없다. 어시스턴트를 기준 시간 넘게 꺼 두었다가 켜면 공백 알림이 한 번 전달된다. 재시작·중복 wake·조건 변경 경합에서 같은 사건의 알림이 중복되지 않고 오래된 조건의 알림이 나가지 않는다.
6. 정한 결정 마감의 알림 시점에 변화가 없어도 마감 알림이 한 번 전달된다. 마감 변경·pause·done·clear 뒤에는 이전 마감 알림이 발생하지 않고, 마감 변경은 비교 기준을 바꾸지 않는다.
7. 대화에서 요청 → 요약 → 확인 → 변화·실패·회복·마감 알림까지 한 흐름이 실제로 이어지고, 대화로 물은 마지막 성공 확인 시각과 상태가 저장된 사실과 같다.

로컬 HTTP 종료 시험은 production 빌드에서 쓸 수 없는 시험용 profile에서 `127.0.0.1/32`만 허용하고 숫자 IP URL로 실행한다(`localhost`는 쓰지 않는다). 내부 주소 거절은 시험용 profile 없이, `tools.ssrfWhitelist`에 사설 대역을 넣은 config에서도 확인한다. 시간 경계 시험은 production CLI/API에서 짧은 주기나 기준 시간을 허용하지 않고, 주입 가능한 시험용 시계로 실제 worker와 로컬 SMTP 경로를 진행시킨다. 위 조건은 042의 **단독 종료 기준**이며, 테스트 green이나 036의 기존 증거만으로 완료 처리하지 않는다.

## 종료 증거 (2026-10-28)

PRD [000](prds/000-web-page-observation-and-condition-decision.md), [010](prds/010-change-failure-recovery-and-gap-notification.md), [020](prds/020-decision-deadline-reminder.md), [030](prds/030-conversational-entrustment-summary-and-confirmation.md)이 각각 독립 Oracle 검토에서 **PASS**를 받고 `Complete (Scoped)`로 닫혔다(000은 10차, 010은 11차, 020은 9차, 030은 23차). 수용 조건마다 owner PRD의 종료 확인이 근거이며, 030의 실제 사용자 흐름이 앞 PRD의 결과를 한 대화와 한 runtime에서 끝까지 이어 확인했다. 이는 현재 self-hosted 지원 범위의 scoped 완료이며 전체 release seal이 아니다.

- 조건 1(030): 실제 `runtime start`의 WebSocket 채널 대화에서 요청에 요약 revision 1과 그 ID·revision의 확인·취소 버튼이 나왔고, 같은 발신자의 `응` 뒤에만 위임·관측·첫 기준·알림 설정·마감이 한 번에 생겼으며 동의 근거는 확인한 요약이었다. 일회성 질문, 애매한 답, 이전 revision의 버튼, 재시작 뒤의 확인은 아무것도 만들지 않았다(QA 22/22). 다른 발신자의 답과 버튼, 가장 최근 응답이 아닌 요약에 대한 답, 지원하지 않는 조건·알림 대상과 볼 값을 찾을 수 없는 페이지의 안내는 실제 agent loop 시험이 확인했다(`spec042_web_watch::conversation::` 41개).
- 조건 2(000, 030): 로컬 HTTP 서버 페이지에서 확인 순간 다시 읽은 값이 첫 기준이 되고 A → 무관한 변화 → B가 무변화·무변화·통지 후보로 남았으며, 확인 순간 값이 바뀌면 다시 확인을 요구했다(000 QA 44/44). 대화 경로에서도 요약 뒤 바뀐 값은 revision 2로 다시 보였고, 페이지에 넣은 지시 문구는 요약과 설정을 바꾸지 못했다(030 QA).
- 조건 3(000): 내부 주소, 사설 주소로의 redirect, userinfo URL은 시험용 profile 없이, `tools.ssrfWhitelist`에 사설 대역을 넣은 config에서도 설정 단계에서 거절됐다. 정적 내용에서 볼 값의 앞뒤 고정 문구를 찾을 수 없는 페이지는 성공을 합성하지 않고 `static_content_unavailable`로 남았으며(000 시험), 마지막 성공 확인 시각과 현재 상태를 CLI/API로 조회했다.
- 조건 4·5(010): 기준·무변화·무관한 변화는 침묵하고 B만 이전/새 값·조건·URL·읽은 시각·근거가 담긴 변화 알림으로 한 번 전달됐다. 기준 시간을 넘긴 확인 실패는 실패 알림 한 번, 회복은 회복 알림 한 번이었고 실패 중 변화 알림은 없었다. 기준 시간을 넘게 꺼 두었던 공백은 공백 알림 한 번이었고, 재시작·중복 wake·조건 변경 경합에서 같은 사건의 중복이나 오래된 조건의 알림이 없었다(010 QA 21/21과 010 시험).
- 조건 6(020): 정한 마감의 알림 시점에 변화가 없어도 마감 알림이 한 번 전달됐고, 마감 변경·pause·done·clear 뒤에는 이전 마감 알림이 없었으며 마감 변경은 비교 기준을 바꾸지 않았다(020 QA 22/22와 020 시험).
- 조건 7(030): 같은 runtime에서 대화 요청 → 요약 → 확인 → A, A, 무관한 변화, B(변화 메일 한 통) → 기준 시간을 넘긴 실패와 회복(메일 각 한 통) → 대화로 바꾼 실패 알림 시간(기준 유지)과 조건(새 기준) → 마감 알림(한 통)까지 이어졌다. 대화로 물은 마지막 성공 확인 시각과 그때의 값·알림 대상은 저장된 사실과 같았고, 모든 메일은 정한 주소로 갔으며 URL query가 없었다(030 QA 22/22).

각 PRD의 최종 전체 workspace 실행에서 유일한 실패는 043 종료 때 기록한 Spec034 baseline 실패(`runtime::generated_media_release::runner::fixture::tests::mismatch_uses_isolated_tree`)였다. 남은 제한은 각 PRD의 "검증"에 적은 것과 같다(한 대화에 위임 하나와 한 페이지, 목록 밖 표현은 확인이 아님, 앞선 turn에서 읽은 페이지 내용의 영향, 원격 수신 ACK와 exactly-once 전달 없음 등).
